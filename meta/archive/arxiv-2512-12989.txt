Can Coding Agents Migrate to
Post-Quantum Cryptography?
Abdulmalik Alquwayfili

arXiv:2512.12989v3 [cs.MA] 20 Sep 2026

Saudi Data & AI Authority (SDAIA), Saudi Arabia
aalquwayfili@ncai.gov.sa

Abstract: A program migrated to post-quantum cryptography
can verify its own signatures while producing keys or signatures
that another implementation rejects. We introduce a contractbased task for migrating a Go file signer from RSA to MLDSA-44, and compare coding agents with and without structured
checker feedback. Both conditions receive the contract, compiler,
documentation, and OpenSSL. Across 160 attempts in four localagent configurations, twelve final patches pass local verification
but fail external requirements. Checker access does not increase
the observed completion rate in any comparison. Recorded traces
show unresolved defects and checks invoked only after a patch
is correct. Serving settings also affect completion: reducing only
Qwen3.8’s context window from 128K to 32K lowers full passes
from 36/40 to 4/40. Four exploratory trials using GPT-6 Astra
through Codex and Claude Fable 5.1 through Claude Code pass
all 40 checks, including both baselines. These findings support
evaluating interoperability separately from local agreement and
reporting harness and serving limits alongside agent results.
Index Terms: post-quantum cryptography, code migration,
coding agents, interoperability

I. I NTRODUCTION
Migrating a signature application to ML-DSA requires more
than replacing the signing function.1 The application must
read and write usable keys, sign the intended message, and
distinguish an invalid signature from an input it cannot process.
FIPS 204 specifies ML-DSA [1]; the application must also
define the interface and data formats that other software will
use.
A local sign–verify test can miss a mistake shared by
both operations. In two recorded attempts, the application
wraps packed key bytes in PEM and reads them back with
a matching loader. Local signing and verification pass, but
OpenSSL rejects the files because the required key structures
are missing.
Figure 1 illustrates the same problem with context: signing
and verification agree on an empty context, but an independent
verifier rejects the signature under the required nonempty
context. ML-DSA permits empty contexts [1], [2]; the error is
ignoring this application’s requirement.
When a coding agent writes both a migration and its tests,
a shared mistake can go undetected. Compilation catches type
and API errors; verification by a separate implementation tests
agreement on message bytes, context, and key encoding. The
question is whether diagnostics from these checks help the
agent repair its mistakes.

We compare two ways of giving an agent feedback during migration. Both conditions receive the same application,
contract, documentation, compiler, and OpenSSL installation.
The baseline can write tests and check interoperability itself.
The feedback condition also has optional access to structured
diagnostics from an external checker. Both have the same
editing budget, and a common final evaluator checks their
patches on fresh inputs. This comparison asks whether structured diagnostics help beyond access to the verification tool.
The task uses CIRCL and specifies persisted keys, a fixed
signing context, and separate responses for invalid signatures
and malformed inputs. We evaluate four local-agent configurations with 20 paired baseline–feedback attempts each,
plus four exploratory trials with Codex and Claude Code.
Twelve patches pass the local round trip while failing external
requirements; no comparison shows a higher completion rate
with checker access.
The study contributes a reproducible migration task and
checker, four comparisons of optional feedback, an ablation
that changes only Qwen3.8’s served context window, and
recorded examples of incomplete repairs. Within each feedback comparison, the model and environment remain fixed.

II. R ELATED W ORK
Post-quantum migration. Strauss et al. examine cryptographic use in Android applications and explore LLMassisted migration, reporting difficulties with dependencies
and changes across files [3]. Pallarés de Bonrostro et al.
evaluate zero-shot and fine-tuned models on paired Python
fragments and examine migrations in open-source projects [4].
Their functional tests give each migration category executable
acceptance criteria. The illustrated signature validator checks
a local sign–verify round trip before and after migration. This
establishes local agreement in each branch; it does not by
itself test whether the migrated application exchanges keys
and signatures with another implementation.
Zhang’s AQuA vision places verification alongside cryptographic discovery and refactoring [5]. Its proposed workflows
combine regression tests, differential and metamorphic testing,
and selected analyses of side-channel behavior. AQuA sets out
a research agenda for migration tools. Our study evaluates a
concrete file-signer migration that preserves the interface and
specifies messages, context, persisted keys, and rejections.
Independent checks. A test oracle judges whether observed
behavior is correct. Barr et al. survey oracles derived from
specifications, contracts, and other evidence [6]. Differential
testing uses disagreement between implementations to expose
possible faults, as Csmith does for compiler outputs [7].
In cryptographic software, Frankencerts generates certificates
from mutated components and compares validation decisions
across SSL/TLS implementations [8]. MLCerts learns certificate representations with generative language models and samples synthetic inputs for differential testing [9]. Our checker
exchanges keys and signatures across implementations under
a declared application contract. Because ML-DSA supports
randomized signing, the relevant observations are successful
key loading, acceptance of valid signatures, and rejection of
invalid ones, rather than identical signature bytes.
Coding agents. SWE-bench evaluates repository patches
using tests for real GitHub issues [10]. SWE-agent lets models
navigate repositories, edit files, and run programs [11]. Suresh
et al. give a post-task memory curator read-only environment
tools to check lessons before reuse [12]. Kiecker et al. study
iterative repair across code generation, test generation, and
translation, finding that most gains occur in the first few repair
iterations [13]. Their workflows return validation failures to
the model. Our comparison leaves checker invocation to the
agent, distinguishing access to diagnostics from a workflow
that delivers them after each failed validation.
Security evaluation. BaxBench uses functional tests and
executable exploits to show that generated backends can
pass functional tests while remaining vulnerable [14]. MPCPatch-Bench examines repairs in multi-party computation software [15]. Its verifier combines comparisons against plaintext
oracles with static checks for security violations. In the reported protocol, patches that pass the functional tests undergo
this additional evaluation.
Chai uses agent-guided differential testing to discover cryp-

tographic misuse and traces library discrepancies into downstream applications [16]. It replays and minimizes discrepancies, classifies their consequences, and retains human review
before reporting. Its use of independent implementations to
guide an agent is closely related to our feedback setting.
We examine whether access to these diagnostics during
repair helps an agent meet a migration contract within a fixed
budget. The comparison holds the agent, editing interface,
and development tools fixed. Both conditions can write tests
and use OpenSSL; one also receives checker feedback, and a
separate evaluator assesses their final patches. Our outcome is
contract compliance: a context or key-format error need not
be exploitable.
III. M ETHOD
The agent edits the application to meet a written contract.
An external checker tests the patch through its public interface
(Figure 2). During development, its diagnostics are available
only in the feedback condition.
A. Task
The reference is a file signer with three entry points:
keygen, sign, and verify. Keys persist on disk and
signatures are stored separately from the input file. The migration preserves these entry points while changing the signing
primitive. The legacy version computes a SHA-256 digest and
signs it with RSA-2048 using PKCS#1 v1.5. The migrated
version passes the original file bytes to Pure ML-DSA-44,
without an application-level prehash.
Both signing and verification use filesigner/v1 as
their context, a requirement introduced by the migration. The
reference passes this value directly to CIRCL’s signing and
verification functions [17].
Persisted keys must be usable by the external implementation without conversion. Public keys use PEM-wrapped SubjectPublicKeyInfo; private keys use PEM-wrapped PKCS#8.
The reference writes the ML-DSA seed and expanded key
together and checks their agreement when loading that form.
Signing uses the library’s randomized mode, so acceptance
depends on verification, not a fixed signature byte string.

Rejection tests modify the message, use a different key,
change or remove the context, and corrupt the signature. The
checker also tests truncated signatures and unparseable keys.
Persistence checks write and reload keys before signing and
verifying again.
C. Outcomes
The contract distinguishes a cryptographic rejection from
malformed input and execution failure. The application returns
exit code 1 for an invalid signature and code 3 for malformed
input. The checker compares the observed response with
the required response for each case; an expected rejection
counts as a passed check. It records contract failures, missing
dependencies, and execution errors separately.
The checker identifies timeouts, signals, and Go runtime
failures before interpreting an exit code. This prevents a
crash from counting as a correct rejection. Validation controls
exercise context mistakes, unconditional acceptance, incorrect
error codes, and faults in the checker. Correct implementations
are included as controls for false failures. The v4 reference
passes all 40 checks, and the evaluator detects all 16 validation
controls, including through the isolated scoring path. These
validate the study’s machinery and are excluded from agent
results.
D. Feedback
In the feedback condition, the agent issues check as a
standalone action. The host returns build status and named
outcomes, including expected and observed responses where
they differ. The agent can use these diagnostics to revise its

patch within the remaining budget. Final evaluation follows
editing and supplies no repair feedback.
IV. E VALUATION
A. Comparison
We compare final correctness, errors missed by local checking, and checking cost. Both conditions receive the full contract, RSA source, documentation, compiler, and OpenSSL.
The baseline can write interoperability tests; feedback also
provides check. Development and final builds share an offline
proxy containing only CIRCL and golang.org/x/sys.
OpenSSL is available during development and to the final
evaluator, but absent from the scored candidate’s runtime.
All local configurations use mini-swe-agent 2.4.6 [11] with
LiteLLM 1.100.1. The first comparison uses Qwen3-Coder30B-A3B-Instruct [18] through vLLM 0.24.0, with float16
weights and a 32,768-token context. Sampling uses temperature 0.7, top-p 0.8, top-k 20, and repetition penalty 1.05.
Each local attempt allows 60 model requests, one hour including model and checking time, and at most 8,192 output
tokens per response. The prompt describes a limit of 60
commands, but the harness counts model requests, including
rejected responses. An attempt can therefore exhaust its budget
before executing 60 commands; we report executed actions
separately.
We run Qwen3.8-27B [19] in Q4_K_M precision through
llama.cpp, revision 4a89937, with a matching Q8_0 multitoken prediction (MTP) draft head from ggml-org [20] and
a 131,072-token context. Thinking and retention of prior
reasoning are enabled. Sampling uses temperature 1.0, topp 0.95, top-k 20, and min-p 0; the request timeout is 1,500

seconds. The task, prompt, parser, development tools, final
evaluator, and request, time, and output budgets remain the
same. A second Qwen3.8 batch changes only the served
context window to 32,768 tokens. We retain the same weights,
draft head, inference engine, sampling, and paired seeds.
The fourth configuration uses Nemotron 3.5 Lightning (30B
parameters, 3B active) [21] in Q4_0 precision with a matching
Q4_0 MTP head [22]. It uses the same llama.cpp revision,
131,072-token window, agent harness, tools, and budgets as
Qwen3.8. Thinking and retention of prior reasoning remain
enabled. Sampling uses temperature 1.0, top-p 0.95, top-k 0,
and min-p 0.
Each comparison uses 20 paired seeds, one attempt per
condition and seed, in baseline–feedback order. Qwen3-Coder
attempts run sequentially on two RTX 8000 GPUs. The
Qwen3.8 and Nemotron batches run one server per GPU and
two attempts at a time. Odd and even seeds use different
GPUs; each seed’s baseline and feedback attempts use the
same GPU. No unrelated benchmark traffic shares the servers,
although concurrent workers share the host CPU.
The Qwen3.8 128K comparison follows the Qwen3-Coder
and native trials. Its setup pilots exposed timeout and context
limits, which informed the serving configuration. All setup
pilots and serving probes are excluded. The 32K ablation
and Nemotron batch follow the 128K comparison. The shared
build/test/repair instruction predates all four counted comparisons. Settings and identities were frozen before each batch,
using the same analysis rules. Comparisons across models
also change precision, inference engine, context, sampling, and
load; they are not controlled estimates of model capability.
Each attempt starts in a fresh workspace. The agent’s final
patch is the workspace left when it submits or reaches a
stopping limit. An agent exit on a model or format error is
also scored. Repetitions measure variation on this task, rather
than adding new migration tasks. Each run records its prompt,
model revision, sampling settings, seed, limits, and stopping
reason.
B. Native agents
After the Qwen3-Coder study, we run one baseline and
one feedback attempt with each of two native coding agents:
Codex CLI 0.154.0 with gpt-6-astra, and Claude Code
2.1.272 with claude-fable-5-1, both at high reasoning
effort. They receive the same task, starting source, offline
dependencies, and final evaluator. Within each agent, prompts
differ only in checker access. External network access is
restricted to the model providers.
The limits remain one hour and 60 tool actions. Native
file edits and shell commands count as actions; these units
differ from the local comparisons’ executed shell steps. The
CLIs also manage context differently. Claude commands have
a 120-second timeout; Codex chooses command timeouts and
uses an auxiliary approval model. Native trial identities are
labels, not controlled sampling seeds. We report these runs
as individual agent-configuration cases, separately from the
paired comparisons.

C. Final checks
Final evaluation rebuilds a snapshot of the selected patch
and tests it with fresh inputs. The source snapshot is mounted
read-only; compilation writes the binary to a separate output
directory. Both conditions use the same evaluator and a 30second limit per candidate invocation. The scored program
receives the files needed for each operation. Isolation probes
check that the agent and scored program cannot access the
reference, checker, or other protected files.
The external checker includes a local sign–verify round trip,
allowing the same final patch to be classified by local and
external outcomes. A patch may pass the local check and fail
an interoperability requirement. The starting application has
no tests; agent-written tests are retained in the development
trace and reported separately.
D. Measures
The primary outcome is the share of valid counted attempts
passing every final check. Failed builds and unsuccessful
repairs stay in the denominator. We report counts, 95% Wilson
intervals, the difference in percentage points, and paired-seed
outcomes: both pass, baseline only, feedback only, or neither.
Pre-action infrastructure failures and independently verified
external outages are logged before final scoring and retried
from the starting state with the same seed. Interruptions and
replacements are disclosed; candidate failures remain scored.
Execution errors, missing dependencies, and cryptographic
rejections remain distinct. A local pass with an external failure requires an observed failed requirement. Missing checks
remain unassessed. We retain raw verdicts but do not infer
rejection defects when required test inputs could not be
constructed.
Per-property results cover messages, context, keys, persistence, and rejections. Repair costs are median and interquartile
range of executed actions, development checker calls, and
elapsed time. Checking consumes both conditions’ time budgets.
Prompt growth is measured from each response’s reported
input tokens, including cached inputs. Claude events sharing
a response identifier count as one request. In the context
plot, medians and interquartile ranges use the attempts still
running at each request; they do not represent a fixed cohort
throughout.
Examples follow the selection rules fixed before collection:
the lowest seed with a local pass and external failure in each
condition, the lowest feedback seed with a diagnostic followed
by a relevant edit and later pass, and the lowest seed with an
unsuccessful feedback repair. Each example retains its final
outcome. Figures 1 and 2 remain illustrations, separate from
these recorded attempts.
The public release contains the code and recorded measurements. Raw trajectories and generated candidate sources are
retained privately.

V. R ESULTS

A. Final correctness
Checker access does not increase the observed full-pass
rate in any comparison (Table I). Qwen3-Coder passes 0/20
in each condition, with a 95% Wilson interval of 0–16.1%.
Qwen3.8 at 128K passes 18/20 in each, with an interval of
69.9–97.2%. Nemotron 3.5 Lightning passes 0/20 in each.
The observed difference is zero percentage points in those
three comparisons; at 32K Qwen3.8 passes 3/20 without and
1/20 with the checker. Their intervals are 5.2–36.0% and
0.9–23.6%, respectively, with an observed difference of −10
percentage points. These samples do not establish equivalence
or a reliable feedback advantage.
All 20 Qwen3-Coder and all 20 Nemotron seed pairs fail
in both conditions. For Qwen3.8 at 128K, 16 pairs pass in
both, two pass only in the baseline, and two pass only with
feedback. At 32K, three pass only in the baseline, one only
with feedback, and 16 fail in both. All 160 counted attempts
receive final scores, with no infrastructure exclusions, replacements, or final checker execution errors. Source inventories,
prompt hashes, model records, and sampling settings match
their respective frozen configurations.
For Qwen3-Coder, 13 baseline and 17 feedback patches
compile, but this difference does not carry through to complete correctness. The four local passes in each condition all
have at least one external-compatibility or required-rejection
failure. Thus, the common local round trip would accept eight
final patches that the contract-based evaluation rejects. This
comparison uses the same patch and fresh evaluation inputs
for both kinds of check; it does not rely on the agent’s
description of its tests. The 32K Qwen3.8 batch adds one localpass/external-fail patch and Nemotron adds three, bringing the
total to twelve across the local configurations.

B. Qwen3-Coder failures
Key handling blocks interoperability early. OpenSSL cannot
load the public key from any of the 30 built patches, while it
loads the private key from one feedback patch. Both directions
involving independently generated OpenSSL keys also fail
for every built patch (Table II). The independent OpenSSL
key-generation and signing setup checks pass in all 30 built
evaluations.
A failed prerequisite can produce several later failures. If
OpenSSL cannot read an application key, it cannot create the
wrong-context signature needed for a rejection test. A later
failure to read that missing signature does not show that the
application accepts an incorrect context. We retain the raw
verdicts for the primary outcome and trace their prerequisites
before attributing semantic errors.
Build failures also have different causes. Four baseline
patches and one feedback patch stop at compiler errors such
as undefined APIs or unused variables. Two patches in each
condition import CIRCL components whose transitive dependencies are absent from the offline proxy. A further baseline
patch deletes go.sum and adds a replacement path into
its temporary module cache; its final read-only build stops
when Go tries to update checksums. These are failures under
the recorded build environment, not evidence about signature

D. Context window
Reducing only Qwen3.8’s served window from 128K to
32K lowers full passes from 36/40 to 4/40 across the two
conditions. Matching condition and seed, 33 attempts pass at
128K and fail at 32K, three fail at both, three pass at both, and
one passes only at 32K. Six patches compile at 32K, compared
with 38 at 128K.
Retained history competes with the next response for the
context window (Figure 3). As the prompt grows, the server
can shorten the response allowance; an oversized request is
eventually rejected. At 32K, 21 attempts stop on context errors
and 19 on repeated unparseable responses. Nine of the latter
end with three consecutive responses that reach their output
limit with reasoning but no command. This is one observed
route to a format stop, not an explanation for every such
stop. None submits voluntarily, compared with 27/40 at 128K.
Nevertheless, four saved patches pass all checks after 18–26
executed actions.

E. Nemotron outcomes
Nemotron 3.5 Lightning completes 0/20 migrations per condition at 128K. Twenty-eight attempts exhaust the 60-request
budget and twelve stop on repeated unparseable responses.
There are no context-limit errors; the largest recorded prompt
contains 78,455 tokens, below the 131,072-token window.
Six patches compile and pass 12–25 checks. Thirty attempts
execute commands but leave a failed build, including imports
unavailable in the offline module cache. Four execute no
command before a format stop. All forty remain in the
denominator.
The three local passes all fail external requirements. Only
two feedback attempts invoke the checker, once each, and both
checks fail. The median attempt executes 56 actions and takes
5.3 minutes across conditions. These runs reach request or
format limits well before the one-hour cap; their speed does
not imply progress toward a correct migration.
F. Feedback and cost
For Qwen3-Coder, sixteen of the 20 feedback attempts
invoke the checker: ten once and six twice. Four never use
it. Checker access therefore measures the effect of making
diagnostics available, not an intervention that forces an agent
to use or act on them. The baseline remains free to run
OpenSSL directly.

VI. R EPAIR A NALYSIS
A. Local agreement, incompatible keys
In Qwen3-Coder, baseline seed 5 and feedback seed 4 are
the first eligible local-pass, external-fail examples. Both write
CIRCL’s packed key bytes directly inside PEM blocks labeled
PRIVATE KEY and PUBLIC KEY. Their loaders reverse that
operation with UnmarshalBinary. These two sides agree,
so local signing and verification pass. The stored bytes do
not contain the required PKCS#8 and SubjectPublicKeyInfo
structures, and OpenSSL rejects both key files.
Each final evaluation records 22 passes and 18 failures
(Figure 4). Those failures include malformed-length signatures
returning the invalid-signature code and deterministic signing
where the contract requires randomized signing. The wrongcontext and empty-context rejection rows, however, depend on
signatures that OpenSSL cannot construct with the incompatible keys. They do not establish independent context-rejection
defects.
Feedback seed 4 receives the key-loading diagnostics, reads
library documentation, and then tests local key generation,
signing, and verification. Those local tests succeed. The final
migration source is unchanged from the checked version,
leaving the external failures unresolved. The example shows

why repeating a successful local test cannot settle a key-format
mismatch identified by another implementation.
B. A repaired context mismatch
Feedback seed 7 is the lowest seed with a diagnostic,
relevant edit, and later pass on the diagnosed check. Its first
checked version calls sk.Sign without a context, while
verification supplies filesigner/v1. In the pinned CIRCL
version, that signing method uses an empty context [17]. The
checker reports failed local verification. The agent reproduces
the failure and replaces the signing call with SignTo, supplying the required context explicitly.
The second development check passes local verification and
three related verification checks. Between the two checked
source versions, the signing call and signature-buffer allocation are the only functional changes. The source remains
unchanged at final evaluation, which again records 22 passes
and 18 failures. OpenSSL key loading and the randomizedsigning requirement still fail. This repair is observed within
one feedback attempt and does not establish a causal advantage
over the baseline.
This observed context mismatch differs from the teaser’s
illustrative shared mistake. Here, signing and verification use
different contexts, so even a local test can expose it. The
recorded examples in which local agreement hides an external
failure concern key encodings.
C. An unsuccessful repair
Feedback seed 1 is the first unsuccessful feedback repair.
It binds the return values of key generation in reverse order,
then passes the resulting public-key object to a private-key
marshaler. The checker reports the key-generation failure. Two
later source rewrites retain the faulty binding and marshaling
call. A combined build-and-check shell command also fails to
invoke the host’s standalone checker action.
The final source compiles but cannot generate its keys.
Evaluation records 9 passes, 30 failures, and an unassessed
signature-size row. Many failures follow from missing keys or
signatures; they are not 30 independently identified bugs. The
trace shows that receiving diagnostics and making subsequent
edits is insufficient evidence that the reported defect was
repaired.

VIII. L IMITATIONS
The study covers one Go file signer and one ML-DSA
parameter set. Repeated attempts do not establish performance
across repositories or production migrations; the four native
trials cannot estimate success rates. The Qwen3.8 configuration was selected after inspecting excluded setup pilots. Across
model configurations, only the Qwen3.8 window ablation
changes a single serving parameter. Other configurations differ
in quantization, sampling, architecture, or inference engine,
so cross-model differences cannot be attributed to the model
alone. OpenSSL is the only external implementation, and the
task’s key-format requirements are a substantial part of its
difficulty.
The offline proxy excludes dependencies outside the supplied cache, including those required by some CIRCL import
paths. One model repeatedly imports an unavailable package,
so this constraint contributes to its failures. Near the context
limit, the runtime can reduce the response allowance before
rejecting an oversized request; reasoning retention and response parsing therefore affect which limit ends a run. Final
builds use read-only snapshots, retaining workspaces after
context, output, or step limits. These shared constraints affect
observed success and limit comparisons with unrestricted
coding environments.
The checker exercises selected contract behaviors. Knownanswer tests are not integrated; neither a local pass nor a full
checker pass would establish FIPS conformance, side-channel
resistance, or deployment safety.

VII. D ISCUSSION
Independent checks expose errors that local round trips
miss, but diagnostics alone need not supply the knowledge
or editing strategy needed for repair.
The key examples suggest verifying key exchange before
signature and rejection behavior. Otherwise, one serialization
error can produce several dependent failures. Diagnostics that
identify these dependencies may help agents prioritize repairs;
this study does not test that interface.

defect unresolved. Qwen3.8 at 128K checks patches that

IX. C ONCLUSION
We evaluate post-quantum migration against a contract and
independent key and signature exchange. Across 160 attempts
in four local-agent configurations, optional checker access
does not increase observed completion. Twelve patches pass
local verification but fail external requirements. Reducing only
Qwen3.8’s context window lowers full passes from 36/40 to
4/40; Qwen3-Coder and Nemotron complete none. All four
native-agent trials pass, including both baselines. Migration
evaluation must distinguish local agreement from interoperability and report harness and serving limits. Diagnostics can
expose defects without ensuring repair.
