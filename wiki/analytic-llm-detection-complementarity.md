# Analytic–judge detection complementarity

Two detectors of code errors can have different failure modes. An LLM judge reads the code and explains what it sees, but it misses many errors. A rule-based checker finds only the error types written into it, yet some of those are errors the judge does not find. The COBOL study measured what each one finds and what happens when both run.

The judge alone was weak. Across the four production judges, the study reports that LaaJ "alone detects only about 45-63% of the errors present in the code."[^c1] The checker alone, in the paper's words, "lacks explanatory depth".[^c2] Combined, the two reached up to 74% coverage and "produces qualitatively richer, more accurate explanations."[^c3] Most of the gain was not a stronger judge. "Most of the improvement stems from capturing analytic-only errors previously missed by the native judges," while performance on native-only and overlap errors stayed stable or rose slightly.[^c4]

The mechanism behind the complement is partly my inference. The checker applies fixed pattern-matching to the program, so an error that matches one of its patterns is found whatever else the judge is attending to. The judge reasons about meaning and can explain, but it does not reliably see the local patterns it was never told to look for. Which errors fall in each set is set by how the checker's patterns were written, so the complement is only as wide as that rule set.

## What the percentages are relative to

The true number of errors in each program is unknown. The authors "approximated" it instead: "the union of errors detected by the analytic tool and by the native judge," counted without double-counting the overlap.[^c5][^c6] This has a consequence the paper does not discuss. An error that both detectors miss is in neither count, so coverage is measured against what the two detectors can see, not against what is in the code. The percentages are therefore recall relative to a floor, and the text gives no way to tell how far below the true total that floor sits. The comparison between the native judge and the hybrid is fair within this setup, because both are scored against the same union. The absolute numbers are not recall in the ordinary sense.

## Shared origin

The checker's error types came from the same expert review that studied the judges' failures: "Drawing on domain expertise, we manually analyzed the" judges' outputs to find their recurring blind spots.[^c7] The checker and the judge were therefore shaped by one set of observations. They are not two independent samples of what could go wrong. The held-out test set is the paper's guard against overfitting. It was "reserved exclusively for evaluation,"[^c8] but it was generated by the same model family as the development set, and it was validated by the same kind of expert review.[^c9] A held-out split does not make the two detectors independent of the people who wrote them.

## Limits

- One domain. The authors say the categories "may generalize to other domains,"[^c10] and do not test that. The checker is a hand-built rule set of over 30 types for one language and one industrial pipeline.
- The checker's own coverage is not reported as a number in the text I read. "Lacks explanatory depth" is qualitative, so the size of the checker's contribution alone is not known.
- The "qualitatively richer" explanations are an abstract-level claim. The text gives no measure of explanation quality beyond that phrase.
- The union denominator (above) was built from the same two detectors being compared. It cannot show how many errors both missed.
- A hybrid is not free of the cost named in [[hint-induced-focus-narrowing]]: the judge can lose some of the issues it would have found unprompted while gaining analytic-only ones. The complement is a net count here, not a guarantee that no judgment is lost.
- Maintenance of the rule set as new error types appear is not discussed.
