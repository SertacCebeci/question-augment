# CodeRefuser — task-level abstention for code generation

> Whether to abstain from a code-generation task is a different question from
> whether one generated sample is wrong: task [[abstention]] asks it *before*
> committing to any sample, and CodeRefuser answers it with a finite-sample,
> distribution-free guarantee instead of a heuristic score threshold.

## Definition / Mechanism

Zhou et al. (2026) separate **task abstention** from sample-level
hallucination detection: "Sample hallucination detection aims to detect
individual code snippets generated by the model that cannot be executed as
expected. In contrast, task abstention aims to identify the prompts for
which an LLM is unlikely to generate the correct answer, even if the LLM is
allowed to produce a high volume of samples." A refusal function $r:
\mathcal{X}\to\{0,1\}$ is desirable when the LLM is unlikely to produce a
functionally correct snippet for the task at all.[^c1]

Correctness is scored by $H@k$, "the probability that $k$ randomly generated
samples are all incorrect," estimated from $n>k$ generated samples with $c$
correct ones. The **(k,α)-criterion**: "The given LLM should refuse the code
generation task if its H@k metric exceeds a threshold α," where α is a
risk tolerance fixed in advance.[^c2]

CodeRefuser calibrates the refusal rule with the Learn-Then-Test (LTT)
framework (Angelopoulos et al., 2025): a threshold $\lambda$ is chosen on a
[[calibration]] set $D_\mathrm{cal}=\{(x_i,t_i)\}$ of (prompt, oracle test cases)
pairs via multiple [[hypothesis-testing|hypothesis testing]] so that, for a new i.i.d. test prompt
$x_\mathrm{test}$, "with a confidence of at least $1-\delta$, the model will
either admit the task, in which case H@k is controlled to be below α, or it
will abstain" — formally $P(\hat R(x_\mathrm{test};\lambda)\le\alpha)\ge
1-\delta$.[^c3]

At test time no oracle tests exist, so the rule scores a task by clustering
the LLM's own generated code samples by execution output on LLM-generated
test cases: samples in the same cluster behave identically on every test
case. Two score functions are built on these clusters — a confidence-based
score (relative size of a sample's cluster) and a [[semantic-entropy]]-based
score (diversity of the cluster distribution) — and refusal fires when no
cluster reaches a calibrated consensus threshold (Cluster Ratio mode) or
when cluster-distribution [[entropy]] exceeds a calibrated threshold (Semantic
Entropy mode). Because LLM-generated test cases can themselves be invalid, a
**Sample-Test Dual Filtering** step first prunes tests with high failure
rates or high output-entropy (signals of undefined behaviour) before
clustering.[^c4]

## Why it matters

Across HumanEval and MBPP with four open-source code LLMs, CodeRefuser's
best configuration achieves "26.5% absolute improvement compared to the best
existing competitor in terms of abstention precision," beating both
static-score baselines (perplexity, NLI self-consistency) and an
execution-based sample-level detector adapted to the task level (CodeHalu).
The authors attribute the gain to two separable pieces: execution-based
scoring beats linguistic/semantic-reasoning scores for code, and the dual
filtering of generated tests is "crucial for the effectiveness" once
execution scoring is used.[^c5]

## Transfer

| | |
|---|---|
| **In its home field** | Learn-Then-Test (Angelopoulos et al., 2025) gives a distribution-free, finite-sample high-probability risk-control guarantee for a general prediction/selection system, given i.i.d. calibration data and a bounded risk function |
| **Here** | used to calibrate a refusal threshold for whether an LLM should attempt a code-generation task at all, before any answer is trusted |
| **What survives** | the finite-sample, distribution-free guarantee (Eq. 5) and its dependence only on i.i.d. calibration/test data, not on knowing the true error distribution |
| **What does not** | the guarantee needs oracle test cases at calibration time (unavailable at test time, worked around with LLM-generated tests and the STDF heuristic, which is not itself covered by the guarantee); the i.i.d. assumption across tasks is explicitly flagged by the authors as strong for practice |

[^c6]

## Limits

The theoretical guarantee (Eq. 5) covers only the calibrated threshold
applied to a score computed from *valid* test cases; the Sample-Test Dual
Filtering step that produces those valid test cases is a heuristic with no
guarantee of its own, so the end-to-end pipeline's risk control is only as
reliable as that filtering. The i.i.d. assumption between calibration and
test tasks is acknowledged by the authors as strong; they support
transferability only informally, by observing that thresholds calibrated on
one dataset (MBPP) still work reasonably on another (HumanEval), not by
extending the proof. The evaluation is confined to two Python benchmarks
(HumanEval, MBPP) and four open-source code LLMs at one default operating
point (α=0.2, δ=0.1, k=3); the source is a single preprint (arXiv, May
2026), not yet peer-reviewed.[^c7]
