Abstract
As Large Language Model (LLM) agents are
increasingly deployed in open-ended domains
like software engineering, they frequently encounter underspecified instructions that lack
crucial context. While human developers naturally resolve underspecification by asking clarifying questions, current agents are largely optimized for autonomous execution. In this work,
we systematically evaluate the clarificationseeking abilities of LLM agents on an underspecified variant of SWE-bench Verified. We
propose an uncertainty-aware multi-agent scaffold that decouples underspecification detection from code execution. Across both proprietary and open-weight frontier LLMs, our
scaffold achieves a 69.40% task resolve rate,
significantly outperforming a standard singleagent setup and closing the performance gap
with agents operating on fully specified instructions. Furthermore, we find that the multi-agent
system exhibits well-calibrated informationseeking behavior, conserving queries on simple
tasks while proactively seeking information on
more complex issues. These findings indicate
that current models can be turned into proactive
collaborators, where agents independently recognize when to ask questions to elicit missing
information in real-world, underspecified tasks.

Introduction

A core property of a good collaborator is the ability
to establish and maintain a shared understanding of
a goal (Clark and Wilkes-Gibbs, 1986). In human
communication, this is rarely achieved through a
single perfectly specified instruction; instead, interlocutors infer missing context and explicitly signal
uncertainty, such as by asking clarification questions (Clark, 1996; Hawkins et al., 2015).
While information gathering in response to underspecification has been studied in the NLP domain, such as in question answering and conversational search (Rao and Daumé III, 2018; Aliannejadi et al., 2019; Zhang and Choi, 2025), these

settings involve static or single-turn interactions
over bounded contexts.
In contrast, modern AI agents are increasingly
deployed in more naturalistic, open-ended domains
such as software engineering. For instance, fixing
real-world GitHub issues (Jimenez et al., 2024) requires exploring, understanding, and editing largescale repositories often containing hundreds of files
and thousands of lines of code, while remaining
aligned with implicit developer intentions. Existing
agents are optimized for autonomous completion
rather than interactive collaboration, creating a critical gap between user intent and agent execution
(METR, 2025; Shen et al., 2026; Wang et al., 2026).
Given these constraints, we investigate the abilities of LLMs to assess uncertainty and determine
how and when to seek information. Specifically, we
consider how models handle external uncertainty:
uncertainty arising from ambiguous or underspecified task inputs, as opposed to internal uncertainty
inherent to the model itself (Li et al., 2026b). While
LLMs can exhibit sensitivity to uncertainty (Kadavath et al., 2022), this is not always robust (Andukuri et al., 2024; Kapoor et al., 2024). Beyond
simply detecting external uncertainty, a true agentic
collaborator must be able to continuously monitor
for such uncertainty and proactively initiate dialogue to elicit missing information. We define such
a system as uncertainty-aware. Importantly, we
use this term in a behavioral rather than formalized
mathematical sense, evaluating how effectively an
agent modulates its information-seeking behavior
based on the severity of underspecification.
We systematically evaluate the clarificationseeking abilities of LLM agents within a dynamic,
multi-turn software engineering framework. We
conduct our evaluation using an underspecified
variant of SWE-bench Verified (Chowdhury et al.,
2024; Vijayvargiya et al., 2026b), where information is removed from the dataset’s original GitHub
issues. To assess the capabilities of agents to act

as question-asking collaborators, we design agent
scaffolds where models must rely on their own calibration of external uncertainty to decide when to
query a user.
Contributions We develop and test both singleand multi-agent frameworks using frontier LLMs
(Claude Sonnet 4.5 and Kimi K2.6) to assess how
agents handle uncertainty arising from underspecified inputs. We find that interactive agents can
successfully identify and retrieve missing information, obtaining a resolve rate comparable to
an autonomous agent provided with a fully specified issue. Our results provide evidence that
some models exhibit well-calibrated clarificationseeking behavior, accurately recognizing when an
issue is already resolvable and refraining from unnecessary interaction. Our code is available at
https://github.com/nedwards99/ask-or-assume.

Related Work

Proactive Dialogue Agents In human communication, interlocutors use clarification requests to
establish shared understanding and resolve ambiguity (Clark and Wilkes-Gibbs, 1986). Recent work
in the NLP domain has considered clarificationseeking behavior in the context of dialogue-based
tasks like open-domain question-answering, conversational search and preference elicitation (Rao
and Daumé III, 2018; Aliannejadi et al., 2019; Kim
et al., 2024; Li et al., 2025; Zhang and Choi, 2025;
Zhang et al., 2025).
To elicit these proactive clarification-seeking behaviors, prior work has explored various methodological approaches. For instance, Zhang et al.
(2025) propose modeling the utility of future conversation trajectories to teach LLMs when a question is necessary; Andukuri et al. (2024) utilize simulated self-play to iteratively improve the model’s
clarification skills; and Testoni and Fernández
(2024) introduce an uncertainty-guided approach,
demonstrating that leveraging a model’s own uncertainty (operationalized as predictive entropy) to
trigger questions is more effective than imitating
human clarification-seeking behavior. While these
methods have proven effective in bounded conversational settings, our work extends this paradigm
by evaluating how agents dynamically elicit missing information in open-ended, multi-step software
engineering environments.

Agentic Systems for Ambiguous Code Generation As LLM agents are increasingly deployed
in software engineering, robustly handling ambiguous or underspecified instructions presents a major
challenge. Existing coding environments used to
evaluate clarification-seeking behaviors often focus
on tasks targeting edits to isolated functions, typically allowing only a single, predetermined round
of clarification or short, constrained exchanges (Li
et al., 2023; Mu et al., 2024; Wu and Fard, 2025;
Li et al., 2026a).
To improve the clarification-seeking behavior
of agents in dynamic, multi-turn coding settings,
recent literature has introduced training pipelines
leveraging reinforcement learning (Sun et al., 2026)
and contrastive training (Chen et al., 2025) techniques. However, these frameworks often impose
rigid interaction structures. For example, both Vijayvargiya et al. (2026a) and Darji and Lutellier
(2025) strictly constrain question-asking to the very
beginning of the trajectory, deferring all code execution until the initial prompt is disambiguated.
In practice, relevant missing information may
only become apparent after initial exploration of a
codebase. Most closely related to our evaluation
setting, Vijayvargiya et al. (2026b) analyze how
LLM agents handle underspecification in software
engineering tasks. In our work, we demonstrate
that a specialized multi-agent scaffold that decouples underspecification detection from code execution enables agents to navigate underspecified tasks
and actively ask questions throughout a trajectory.
Uncertainty Detection in LLMs A prerequisite
for proactive clarification is an agent’s ability to
accurately gauge its own uncertainty. Foundational
work demonstrates that base LLMs exhibit a degree
of internal calibration, enabling them to estimate
the likelihood of their correctness or express their
confidence in natural language (Kadavath et al.,
2022; Lin et al., 2022). However, this calibration is
not always robust out of the box (Kapoor et al.,
2024; Andukuri et al., 2024), as standard posttraining alignment techniques, such as RLHF, can
inadvertently degrade calibration and encourage
model overconfidence (Zhou et al., 2024). Furthermore, effective interaction requires distinguishing
between different sources of uncertainty. For instance, recent work has highlighted the difference
between uncertainty caused by a model’s lack of
parametric knowledge versus input underspecification or ambiguity (Hou et al., 2024; Zhang and

Choi, 2025). Formally quantifying this distinction,
Li et al. (2026b) distinguish internal uncertainty
(inherent to the model) from external uncertainty
(arising from ambiguous or underspecified inputs).
Our work specifically investigates how agents handle external uncertainty. Rather than considering
a formalized measure of confidence (e.g., a probability), our work evaluates uncertainty detection
behaviorally. That is, we assess whether agents
can reliably identify missing context and resolve it
through asking the user for clarification.

Method

3.1

Dataset and Evaluation Framework

We closely follow and adapt the interactive evaluation setting introduced by Vijayvargiya et al.
(2026b). We use their dataset (CMU LTI, 2024),
which is an underspecified variant of SWE-bench
Verified (Chowdhury et al., 2024), a humanannotated subset of 500 GitHub issues derived from
the original SWE-bench dataset (Jimenez et al.,
2024). To construct their dataset, the authors utilized GPT-4o (Hurst et al., 2024) to summarize issues into underspecified variants, removing important details while preserving repository terminology. Given the automatic nature of the construction
process, we performed an additional spot-check
analysis to verify dataset validity (Appendix A);
concrete examples are provided in Appendix D.
3.2

Agent Design

Agent Framework We use the OpenHands
(Wang et al., 2025) agent framework for all experiments. This framework enables an LLM to
iteratively write, execute, and debug code within
a secure sandbox environment, using tools for
navigating codebases, editing files and executing
Bash/Python scripts. To ensure comparability with
Vijayvargiya et al. (2026b), all agent setups are
provided with a maximum of 100 iterations.
Agent Backbones We evaluate two frontier backbone LLMs: Claude Sonnet 4.5 (Anthropic, 2025),
a proprietary model, and Kimi K2.6 (Moonshot
AI, 2026), an open-weight model. Both perform
competitively in many coding benchmarks, serving
as strong proxies for current agentic capabilities in
interactive software engineering settings.

Uncertainty-Aware Agents

To investigate how agents can independently detect
and resolve underspecification, we propose two
scaffolds. We refer to these as “uncertainty-aware”
since they are designed to adapt their informationseeking behavior based on the extent of missing
context. While these agents can query the same
simulated user as the I NTERACTIVE BASELINE,
they do not rely on a hardcoded interaction prompt,
instead using the default SWE-bench task prompt.
Because they receive no prior warning that the issue
is underspecified, they must independently identify
missing context and query the simulated user only
when they determine it is necessary.
U NCERTAINTY-AWARE (S INGLE ) In this configuration, a single coding agent is prompted at
each turn to check for underspecification and, if
detected, to query the user. We refer to the agent
hereafter as UA-S INGLE.

improve underspecification detection. By assigning specialized roles to multiple LLMs, multi-agent
systems can tackle increasingly complex tasks
(Hong et al., 2024; Qian et al., 2024; Park et al.,

design a multi-agent scaffold consisting of two
agents. The Main Agent is equipped with standard tools to navigate repositories, edit files, and
execute code. The Intent Agent monitors the state

or repository context contains missing information.
The Intent Agent is provided with its own dedicated system prompt (detailed in Appendix B.2)
and has access to a single tool that outputs a binary
decision indicating whether clarification is required.

Claude Sonnet 4.5, UA-S INGLE outperforms the

used the task completion tool to ask questions, highlighting the brittleness of hardcoded prompts and
reliance on underlying model capability.

Conclusion

We investigated the abilities of LLM agents to act
as collaborators by independently identifying missing information and seeking clarification in underspecified software engineering tasks. We introduced an uncertainty-aware multi-agent scaffold
that isolates the role of underspecification detection.
Evaluated on an underspecified variant of SWEbench Verified, this system achieved a 69.40% resolve rate across both proprietary and open-weight
LLM backbones that effectively closed the performance gap with an autonomous agent operating on
a fully specified issue.
Our results show that the multi-agent scaffold
exhibits well-calibrated information-seeking behavior, accurately recognizing when an issue was already resolvable and refraining from unnecessary
interaction on simpler tasks. Our results also reveal
that underlying model capability shapes clarification behavior: while both LLM backbones benefit
from the multi-agent scaffold, Kimi K2.6 exhibits
higher query rates and poorer calibration, suggesting that robust uncertainty-aware interaction may
require targeted training beyond architectural design alone. These findings present a promising step
towards deploying agents not only as autonomous
coding assistants, but as proactive collaborators
capable of detecting and resolving external uncertainty arising from real-world underspecification.

Limitations
User Simulator Our evaluation relies on an
LLM-based user simulator to provide withheld information. While we implemented strict guardrails
to prevent unintended leakage and generally observed reasonable simulator responses, recent studies highlight that LLM-simulated users can be un-

reliable proxies for human behavior, often being
unnaturally cooperative and failing to reflect the
nuance and variance of real human users (Naous
et al., 2026; Seshadri et al., 2026). Results may
therefore vary if real human users interact with the
agents that we presented in this work.
Prompting and Training While our most successful approach relies on a multi-agent scaffold
with tailored prompts for each agent, it demonstrates that frontier models possess the latent capacity to monitor their own uncertainty and proactively seek clarification out of the box. Rather
than relying on prompting specialized agents, future work could explore utilizing these successful interaction trajectories to train single models
with standard finetuning or reinforcement learning
(RL) techniques to natively exhibit this calibrated,
information-seeking behavior (e.g., Andukuri et al.,
2024; Bhargava et al., 2024; Sun et al., 2026).
Model Generalization and Cost Our experiments were conducted using both a proprietary
model (Claude Sonnet 4.5) and an open-weight
model (Kimi K2.6), demonstrating that our multiagent scaffold generalizes across model families.
By relying on frontier models, our evaluation incurred a non-trivial financial cost (detailed in Appendix E). Furthermore, previous studies indicate
that smaller open-weight models severely lack the
calibration required for interactive underspecification (Vijayvargiya et al., 2026b), even with explicit
prompting. The current findings may therefore be
limited to frontier models and may not directly
translate to smaller open-source models.

Ethical Considerations
Our work investigated the ability of LLM agents to
detect external uncertainty and seek clarification on
underspecified software engineering tasks. While
our results demonstrate that uncertainty-aware scaffolds can effectively resolve underspecified GitHub
issues, SWE-bench Verified represents only a subset of software engineering tasks. As such, our
empirical findings should not be extrapolated to
suggest that agents will reliably detect missing information in other, often high-stakes environments,
such as security-critical applications without further experimentation.
We also acknowledge the environmental and financial costs associated with the deployment of
multi-agent systems. As detailed in our cost break-

down (Appendix E), the increased inference overhead in multi-agent systems is a trade-off that must
be weighed against the gains in developer productivity.
AI Use. We used an AI assistant to assist with
experimental code generation, and help improve
the clarity and flow of the writing while revising
the paper. However, all original writing, research
conceptualization, methods, experiments, and analyses were performed by the authors, and any AI
outputs were carefully verified.

A

Dataset Construction and Validation

As mentioned in Section 3.1, we conduct our evaluation using an underspecified variant of SWEbench Verified, directly adopting the dataset introduced by Vijayvargiya et al. (2026b). The authors automatically constructed this dataset through
prompting GPT-4o to summarize the original
GitHub issue. The prompt instructed the model
to retain repository-specific terminology while removing important technical details.
To validate the synthetically generated dataset,
Vijayvargiya et al. (2026b) applied distributional
difference analysis (Zhong et al., 2023), an LLMdriven approach for discovering and describing
differences between corpora, to compare the generated issues against naturally occurring underspecified issues in the original SWE-bench dataset.
Their analysis found that natural issues typically
retain more concrete technical details, such as code
snippets, specific error messages, and file/line references, compared to the generated issues. Beyond
this difference, however, the synthetic and natural issues were not found to be otherwise distinguishable. Consequently, the synthetic generation
process produces instances that are often strictly
more underspecified than natural occurrences. For
our evaluation, this characteristic of the synthetic
dataset is advantageous, making the task more
challenging and heavily penalizing blind execution
while encouraging proactive interaction.
Empirical Spot-Check Analysis To further verify the dataset’s validity for our evaluation, we conducted a manual qualitative analysis on a random
sample of 10 task instances. For each instance, we
compared the original, fully specified issue description with the synthetically generated underspecified
issue description to determine whether the removed
information was necessary for solving the task.
In 5 instances, the removed information was essential for solving the task, such as specific OS
configurations or user-provided value constraints.
In the remaining 5 instances, the summarized description retained sufficient technical details (e.g.,
specific class or method names) to likely allow an
agent to successfully localize the relevant files in
the repository requiring edits to correctly resolve
the issue. Figure 7 illustrates one example of each
case.
Notably, this variance closely mirrored actual
agent performance. For instance, the H IDDEN baseline using Claude Sonnet 4.5 failed to solve all 5

instances where our manual analysis revealed that
essential information was removed, but successfully solved the 5 instances where sufficient technical details were retained. This pattern is consistent
with the significant performance gap between the
H IDDEN and F ULL baselines (54.80% vs. 70.80%
for the Claude Sonnet 4.5 agent), highlighting that
the dataset provides meaningful signal for when interaction is required to resolve underspecification.

B.3

User Simulator Prompt

Figure 5 shows the prompt provided to the user
simulator, adapted from the prompt in Vijayvargiya
et al. (2026b). Initial experiments revealed that the
simulated user occasionally provided misaligned
guidance due to a lack of awareness regarding the
specific constraints of our evaluation environment
(i.e., OpenHands agent in SWE-bench). To prevent
the simulator from misleading the agent or leaking
unintended information, we augmented the original
prompt with the following environment-specific
guardrails:
• Preventing test modifications (Rule 5): In
SWE-bench, test files should not be modified
by the agent. Because the original simulated
user lacked this context, it failed to correct
the agent when it attempted to edit files inside

the /testbed directory. Rule 5 was added to
instruct the simulated user to explicitly remind
the agent of this if it asked about changing test
files.

• Resolving directory mismatches (Rule 6):
Agents in OpenHands operate within a designated /workspace directory, whereas SWEbench imports and runs tests in a separate
/testbed directory. Agents often became
confused when changes in /workspace were
not reflected in the tests run in /testbed.
Rule 6 was added to instruct the simulated
user to explicitly remind the agent of this if it
asked why its edits weren’t being reflected.

Additionally, to prevent unbounded interactions
and encourage efficient information-seeking, the
simulated user is restricted to three interaction turns
per trajectory. After this limit is reached, it issues
a canned response instructing the agent to proceed
with the available information. Note that the I N TERACTIVE BASELINE configuration is explicitly
warned of this limit upfront, while our uncertaintyaware agents are not, testing their ability to independently seek information in an efficient manner.

Question Analyses

C.1

Question Statistics

Table 2 provides a detailed breakdown of
clarification-seeking behavior across the three interactive agent configurations using both LLM backbones.
Regarding the amount of interaction, the I N TERACTIVE BASELINE initiates queries in nearly
all tasks for Claude Sonnet 4.5 (Nask =496, 1.02
Q/Task), but far fewer for Kimi K2.6 (Nask =194,
1.00 Q/Task). This reduction is largely driven by
instruction-following failures, where the model erroneously used the task completion tool to ask
questions rather than initiating a proper query turn,
resulting in many tasks where interaction was attempted but not successfully executed.
In general, the uncertainty-aware agents demonstrate more conservative query initiation but greater
query volume. UA-M ULTI initiated queries in 344
tasks for Claude Sonnet 4.5 and 435 tasks for Kimi
K2.6, engaging in significantly more iterative dialogue (Claude: 3.06 Q/Task; Kimi: 8.71 Q/Task).
The much higher query rate for Kimi K2.6 also reflects the model’s tendency to over-flag underspecification. UA-S INGLE initiated queries in more
tasks with Claude Sonnet 4.5 (Nask =369) but in
fewer tasks with Kimi K2.6 (Nask =167). For both
models, the query rate was substantially lower than
for the multi-agent scaffold (Claude: 1.84 Q/Task;
Kimi: 1.23 Q/Task).
The length of these interactions also varies. For
Claude Sonnet 4.5, the I NTERACTIVE BASELINE
generates highly verbose queries (251.33 tokens)
and receives correspondingly long answers (415.53
tokens), reflecting a strategy to ask for all potentially missing information upfront. In contrast, UA-M ULTI uses the most concise queries
(171.57 tokens) and receives the shortest answers
(173.65 tokens), supporting the observation that the
multi-agent scaffold asks highly targeted, contextspecific questions based on intermediate tool observations (e.g., see Figure 6). UA-S INGLE falls
between the two (181.35/229.76 tokens). For
Kimi K2.6, the pattern differs: UA-M ULTI produces shorter queries (96.73 tokens) but receives
markedly shorter answers (57.06 tokens), suggesting lower-quality clarification requests that elicit
less informative responses. Notably, UA-S INGLE
with Kimi K2.6 asks fewer but more substantive
questions (143.18 tokens) and receives considerably longer answers (247.97 tokens).

Finally, we analyze the temporal distribution of
these queries. We categorize the timing of each
question based on its event ID position within the
agent trajectory, divided into deciles: “Early” (1st–
3rd decile), “Mid” (4th–7th decile), and “Late”
(8th–10th decile). For Claude Sonnet 4.5, the
I NTERACTIVE BASELINE concentrates almost all
questions in the Early stage (97.6%), while UAS INGLE skews heavily Late (43.9%), suggesting
it often attempts code modifications before recognizing an information gap. In contrast, UAM ULTI distributes queries across Early (41.8%)
and Mid (43.4%) stages, reflecting continuous monitoring throughout the trajectory. For Kimi K2.6,
the temporal patterns differ: UA-M ULTI concentrates queries in the Mid stage (46.5%), while UAS INGLE skews Early (51.0%). Notably, the I NTER ACTIVE BASELINE for Kimi K2.6 is heavily concentrated in the middle of the trajectory (66.5%),
in contrast to the Early concentration seen with
Claude Sonnet 4.5, likely reflecting the instructionfollowing failures that disrupted early-stage querying.

Computing Costs

Table 5 details the total inference costs for each
evaluation setting across both LLM backbones. For

executed via the Anthropic API. While the multiagent scaffold more than doubles the total inference

resolving underspecification and significantly increasing the overall task resolve rate, the multiagent setup ultimately saves substantial human developer time and effort that would otherwise be
spent on debugging solutions that are misaligned

API. Kimi K2.6 runs at roughly 30–50% of the

efficiency gains while maintaining competitive performance. Additionally, the multi-agent scaffold
has a total inference cost less than double that of
the single-agent baselines, making Kimi K2.6 a
cost-efficient alternative for deploying the framework.

</WORKFLOW>
