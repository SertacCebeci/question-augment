Client Features Elicitation Copy page Copy page Copy page Copy page Elicitation is newly introduced
in this version of the MCP specification and its design may evolve in future protocol versions. The
Model Context Protocol (MCP) provides a standardized way for servers to request additional
information from users through the client during interactions. This flow allows clients to maintain
control over user interactions and data sharing while enabling servers to gather necessary
information dynamically. Servers request structured data from users with JSON schemas to validate
responses. ​ User Interaction Model Elicitation in MCP allows servers to implement interactive
workflows by enabling user input requests to occur nested inside other MCP server features.
Implementations are free to expose elicitation through any interface pattern that suits their
needs—the protocol itself does not mandate any specific user interaction model. For trust &amp;
safety and security: Servers MUST NOT use elicitation to request sensitive information. Applications
SHOULD : Provide UI that makes it clear which server is requesting information Allow users to review
and modify their responses before sending Respect user privacy and provide clear decline and cancel
options ​ Capabilities Clients that support elicitation MUST declare the elicitation capability
during initialization : { &quot;capabilities&quot; : { &quot;elicitation&quot; : {} } } ​ Protocol
Messages ​ Creating Elicitation Requests To request information from a user, servers send an
elicitation/create request: ​ Simple Text Request Request: { &quot;jsonrpc&quot; : &quot;2.0&quot; ,
&quot;id&quot; : 1 , &quot;method&quot; : &quot;elicitation/create&quot; , &quot;params&quot; : {
&quot;message&quot; : &quot;Please provide your GitHub username&quot; , &quot;requestedSchema&quot;
: { &quot;type&quot; : &quot;object&quot; , &quot;properties&quot; : { &quot;name&quot; : {
&quot;type&quot; : &quot;string&quot; } }, &quot;required&quot; : [ &quot;name&quot; ] } } }
Response: { &quot;jsonrpc&quot; : &quot;2.0&quot; , &quot;id&quot; : 1 , &quot;result&quot; : {
&quot;action&quot; : &quot;accept&quot; , &quot;content&quot; : { &quot;name&quot; :
&quot;octocat&quot; } } } ​ Structured Data Request Request: { &quot;jsonrpc&quot; : &quot;2.0&quot;
, &quot;id&quot; : 2 , &quot;method&quot; : &quot;elicitation/create&quot; , &quot;params&quot; : {
&quot;message&quot; : &quot;Please provide your contact information&quot; ,
&quot;requestedSchema&quot; : { &quot;type&quot; : &quot;object&quot; , &quot;properties&quot; : {
&quot;name&quot; : { &quot;type&quot; : &quot;string&quot; , &quot;description&quot; : &quot;Your
full name&quot; }, &quot;email&quot; : { &quot;type&quot; : &quot;string&quot; , &quot;format&quot;
: &quot;email&quot; , &quot;description&quot; : &quot;Your email address&quot; }, &quot;age&quot; :
{ &quot;type&quot; : &quot;number&quot; , &quot;minimum&quot; : 18 , &quot;description&quot; :
&quot;Your age&quot; } }, &quot;required&quot; : [ &quot;name&quot; , &quot;email&quot; ] } } }
Response: { &quot;jsonrpc&quot; : &quot;2.0&quot; , &quot;id&quot; : 2 , &quot;result&quot; : {
&quot;action&quot; : &quot;accept&quot; , &quot;content&quot; : { &quot;name&quot; : &quot;Monalisa
Octocat&quot; , &quot;email&quot; : &quot;octocat@github.com&quot; , &quot;age&quot; : 30 } } }
Reject Response Example: { &quot;jsonrpc&quot; : &quot;2.0&quot; , &quot;id&quot; : 2 ,
&quot;result&quot; : { &quot;action&quot; : &quot;decline&quot; } } Cancel Response Example: {
&quot;jsonrpc&quot; : &quot;2.0&quot; , &quot;id&quot; : 2 , &quot;result&quot; : {
&quot;action&quot; : &quot;cancel&quot; } } ​ Message Flow ​ Request Schema The requestedSchema
field allows servers to define the structure of the expected response using a restricted subset of
JSON Schema. To simplify implementation for clients, elicitation schemas are limited to flat objects
with primitive properties only: &quot;requestedSchema&quot; : { &quot;type&quot; :
&quot;object&quot; , &quot;properties&quot; : { &quot;propertyName&quot; : { &quot;type&quot; :
&quot;string&quot; , &quot;title&quot; : &quot;Display Name&quot; , &quot;description&quot; :
&quot;Description of the property&quot; }, &quot;anotherProperty&quot; : { &quot;type&quot; :
&quot;number&quot; , &quot;minimum&quot; : 0 , &quot;maximum&quot; : 100 } }, &quot;required&quot; :
[ &quot;propertyName&quot; ] } ​ Supported Schema Types The schema is restricted to these primitive
types: String Schema { &quot;type&quot; : &quot;string&quot; , &quot;title&quot; : &quot;Display
Name&quot; , &quot;description&quot; : &quot;Description text&quot; , &quot;minLength&quot; : 3 ,
&quot;maxLength&quot; : 50 , &quot;format&quot; : &quot;email&quot; // Supported: &quot;email&quot;,
&quot;uri&quot;, &quot;date&quot;, &quot;date-time&quot; } Supported formats: email , uri , date ,
date-time Number Schema { &quot;type&quot; : &quot;number&quot; , // or &quot;integer&quot;
&quot;title&quot; : &quot;Display Name&quot; , &quot;description&quot; : &quot;Description
text&quot; , &quot;minimum&quot; : 0 , &quot;maximum&quot; : 100 } Boolean Schema { &quot;type&quot;
: &quot;boolean&quot; , &quot;title&quot; : &quot;Display Name&quot; , &quot;description&quot; :
&quot;Description text&quot; , &quot;default&quot; : false } Enum Schema { &quot;type&quot; :
&quot;string&quot; , &quot;title&quot; : &quot;Display Name&quot; , &quot;description&quot; :
&quot;Description text&quot; , &quot;enum&quot; : [ &quot;option1&quot; , &quot;option2&quot; ,
&quot;option3&quot; ], &quot;enumNames&quot; : [ &quot;Option 1&quot; , &quot;Option 2&quot; ,
&quot;Option 3&quot; ] } Clients can use this schema to: Generate appropriate input forms Validate
user input before sending Provide better guidance to users Note that complex nested structures,
arrays of objects, and other advanced JSON Schema features are intentionally not supported to
simplify client implementation. ​ Response Actions Elicitation responses use a three-action model to
clearly distinguish between different user actions: { &quot;jsonrpc&quot; : &quot;2.0&quot; ,
&quot;id&quot; : 1 , &quot;result&quot; : { &quot;action&quot; : &quot;accept&quot; , // or
&quot;decline&quot; or &quot;cancel&quot; &quot;content&quot; : { &quot;propertyName&quot; :
&quot;value&quot; , &quot;anotherProperty&quot; : 42 } } } The three response actions are: Accept (
action: &quot;accept&quot; ): User explicitly approved and submitted with data The content field
contains the submitted data matching the requested schema Example: User clicked “Submit”, “OK”,
“Confirm”, etc. Decline ( action: &quot;decline&quot; ): User explicitly declined the request The
content field is typically omitted Example: User clicked “Reject”, “Decline”, “No”, etc. Cancel (
action: &quot;cancel&quot; ): User dismissed without making an explicit choice The content field is
typically omitted Example: User closed the dialog, clicked outside, pressed Escape, etc. Servers
should handle each state appropriately: Accept : Process the submitted data Decline : Handle
explicit decline (e.g., offer alternatives) Cancel : Handle dismissal (e.g., prompt again later) ​
Security Considerations Servers MUST NOT request sensitive information through elicitation Clients
SHOULD implement user approval controls Both parties SHOULD validate elicitation content against the
provided schema Clients SHOULD provide clear indication of which server is requesting information
Clients SHOULD allow users to decline elicitation requests at any time Clients SHOULD implement rate
limiting Clients SHOULD present elicitation requests in a way that makes it clear what information
