Unit tests help detect faults and prevent regressions, but writing them manually is costly. Automated unit test
generation involves constructing inputs that exercise the code and oracles that express expected behavior.
Large language models (LLMs) can use code and natural-language context to construct tests, but generated
tests may fail to compile or execute, contain invalid assertions, or have limited ability to detect faults. We
conducted a systematic literature review and mapping study of 178 publications with eligible full-text reports
available by 31 July 2026. We organize the literature using a lifecycle-oriented analytical framework that
covers test construction and quality assurance. Across the reviewed studies, context enrichment addresses
missing project information, while iterative validation and repair use compiler and execution feedback to
revise generated tests. These mechanisms help make tests executable, although their contributions to oracle
correctness and fault detection vary across tasks and evaluation settings. Meanwhile, benchmark validity, test
maintainability, and industrial reliability remain open concerns. Finally, we discuss opportunities in evaluation,
context and specification use, hybrid techniques, and agentic workflows.

Introduction

Software testing is a fundamental engineering practice for assuring software quality and mitigating
release risks [39, 128]. Unit testing is a test level that focuses on the smallest independently testable
units of a system, such as a function, method, or class [19]. The tests may be designed using
structural information, externally observable behavior, or both. A well-designed suite of unit tests
can detect logic errors and boundary-case defects early in development, prevent regressions as the
software evolves [210], and support agile practices such as test-driven development [19]. Manually
writing comprehensive, high-quality unit tests nevertheless remains costly and labor-intensive, as
prior surveys report that it can consume more than 15% of development time [39, 151].
To address this challenge, researchers have long studied automated test generation (ATG),
including search-based software testing (SBST) [50, 74, 122] and symbolic or concolic execution [57, 149, 165, 211]. These techniques have proven effective at systematically exploring program
structures. However, their effectiveness depends on the objectives, constraints, and environment
models available. Domain-specific formats, complex object states, and external interactions may
require additional specifications, models, or manual engineering [17, 50, 51, 69, 124, 227], often
limiting their ability to generate realistic test cases.
Large language models (LLMs) provide a complementary way to use learned code and naturallanguage patterns during test construction [31, 170]. LLM-based systems have generated inputs and
fixtures [105, 172], test prefixes [139, 230], and mock implementations for external dependencies [61,
139]. Project tests and documentation can supply examples of API use and descriptions of expected
behavior to guide this generation [77, 232]. These uses motivate the focus of this survey and require
compilation, execution, and oracle validation of the generated tests.
Existing surveys cover LLM applications across software engineering [45, 221], while surveys
of automated test generation compare established generation paradigms [11, 33]. More focused
reviews summarize the use of LLMs in unit testing [215]. For example, Zhang et al. [220] examine
testing tasks, model utilization, and supporting techniques. Our lifecycle analysis asks how project
context, generated candidates, and validation feedback interact during test generation and how
established testing techniques support this process. Section 8 compares these surveys in detail.
Through a systematic analysis of 178 publications, this paper develops a lifecycle-oriented
taxonomy of LLM-based unit test generation. The synthesis focuses on publications in which
unit-test generation is a primary or co-primary objective. The taxonomy organizes the reviewed
methods into test-construction and quality-assurance categories without assuming that every
system follows a fixed sequence. Test-construction approaches usually draw on project context,
retrieval, static analysis, slicing, and feedback, whereas quality-assurance approaches often use
compilers, test runners, search and program-analysis tools, and coverage or mutation feedback.
Within these categories, we compare the information provided to a generator, the test artifact it
constructs, and the checks used to accept or revise that artifact. Compilation and execution are
used to check whether a test builds and runs. However, oracle correctness, fault detection, and
industrial applicability remain open challenges.
To structure our analysis, we address the following research questions (RQs):
• RQ1: How do LLMs support the core phases of test construction, including context analysis,
input generation, and oracle construction?
• RQ2: What mechanisms are employed to validate, repair, and optimize the quality of LLMgenerated tests?
• RQ3: What are the primary challenges in current LLM-based unit-test generation, and what
opportunities do they present for future research?

Background

To situate LLM-based methods, we first review established automated unit test generation approaches and their documented limitations, and then summarize the capabilities and risks relevant
to LLM-based test generation.
2.1

Traditional automated test generation

Automated unit test generation can be analyzed around two central artifact components: a test
prefix, which establishes objects, inputs, and calls needed to exercise the code under test (CUT),
and a test oracle, which encodes expected behavior, commonly through assertions [18, 20, 128].
Fixtures, setup and teardown code, mocks, and environment configuration may support these components. For a test of max(a,b), the prefix supplies numerical arguments and invokes the function,
while the oracle checks the returned value. A function that makes an asynchronous network call
can additionally require a mock that reproduces the session’s behavior [172]. The prefix–oracle
distinction nevertheless provides a useful analytical basis for examining how generation methods
construct executable scenarios and how they infer or obtain expected outcomes. Among established
automated unit-test generation methods, this survey uses two prominent paradigms to frame the
comparison with LLM-based approaches:
Search-Based Software Testing (SBST). SBST frames test case generation as a search-based
optimization problem [70, 124]. It employs metaheuristic algorithms, such as genetic algorithms,
to evolve a set of test cases that maximize a fitness function, which is typically a code coverage
metric like branch coverage [69, 124]. Tools such as EvoSuite [50, 51] for Java and Pynguin [122]
for Python have demonstrated the effectiveness of this approach in exploring program structures.
However, coverage-oriented fitness functions do not directly encode program intent [69]. SBST
may also require many trials when a target depends on domain-specific formats, such as a valid IP
address. Constructing complex object states can also be difficult because a test prefix may require a
precise sequence of method calls within a large search space [51, 74]. External interactions pose a
related challenge when their behavior cannot be represented adequately in the fitness function [51].
Symbolic and Concolic Execution. Symbolic execution provides a systematic approach based
on formal methods [17, 227]. It executes a program with symbolic variables, collects path constraints,
and uses a solver to generate inputs for selected paths. Its principal scalability challenge is path
explosion: the number of feasible paths can grow rapidly with program size, making exhaustive
exploration computationally infeasible. Concolic execution interleaves concrete and symbolic
execution to guide the exploration of new paths, but does not fully eliminate path explosion [60, 154].
Tools like KLEE and Coyote C++ illustrate symbolic and concolic approaches for bug finding and
high structural coverage [149, 227].
2.2

LLMs for code generation

SBST optimizes explicit objectives, whereas symbolic execution solves encoded path constraints.
Project examples and specifications offer complementary guidance when testing requires domainspecific inputs, complex object construction, or models of external services [17, 51, 69]. LLM-based
generation offers one such complement. Large-scale pre-training exposes LLMs to statistical patterns
in code and aligned code–test data [30, 147]. These patterns can guide them to generate semantically
plausible inputs or construct complex objects. LLMs can also adapt their output based on examples
provided in a prompt through in-context learning without parameter updates [14, 131]. Project
context can also supply input constraints, mocking information, and dependency details needed to
construct and execute a test in the target environment. For example, LISP derives input partitions

Research Methodology
Paper collection methodology

Fig. 1 illustrates the systematic literature collection and screening process adopted for this survey.
Final synthesis eligibility was content-based: an eligible LLM or code model had to generate a newly
constructed unit-level test artifact, and unit-test generation had to be a primary or co-primary
research focus. We required an accessible English full text with sufficient technical or empirical
content. Publication venue and status were recorded as study characteristics and did not determine
inclusion. The review cutoff was fixed at 31 July 2026, and reports of the same underlying work
were linked into one study family.
The four core electronic sources were Scopus, Web of Science Core Collection, the ACM Digital
Library, and IEEE Xplore. arXiv and DBLP were used for separately logged supplementary discovery
searches. All six searches were last run on 18 August 2026. Before cross-query and cross-source
deduplication, Scopus contributed 3,141 query hits, Web of Science 1,882, the ACM Digital Library
1,032, IEEE Xplore 4,300, arXiv 3,571, and DBLP 859.
The electronic searches used one broad Boolean query family that required at least one model

Scopus applied their conjunction to TITLE-ABS-KEY, and Web of Science applied it to the TS topic
field. The ACM Digital Library and IEEE Xplore used source-specific translations or partitions to
accommodate their interface and query-length constraints; these adaptations retained the same
search concepts, and all partitioned results were unioned before deduplication. arXiv used a
corresponding partitioned query for supplementary discovery, while DBLP used documented
title/metadata variants because its interface cannot express the complete nested Boolean query. No
lower date limit or filter on venue, document type, language, or access was imposed during retrieval.
The review cutoff and the requirement for an English full text were applied after retrieval during
record management and eligibility assessment. The anonymous replication package provides exact

3.5

Unified taxonomy and research questions

To analyze the collected literature, we use a lifecycle-oriented taxonomy. As illustrated in Fig. 4,
it distinguishes a generation phase that produces test artifacts from a quality assurance and
enhancement phase that validates and refines them. The phases are analytical categories rather
than a strictly linear sequence because many systems return execution feedback to generation.
The generation category covers methods that translate source code and project information into
candidate test artifacts [153, 213]. It includes context analysis, prefix and input generation, and
oracle construction. For context analysis, these methods use static or dynamic analysis to supply
project information and reduce missing-context or compilation failures [152, 197]. Prompting,
fine-tuning [155, 156], and pre-training [3, 147] may support one or more of these tasks. The
quality-assurance and enhancement category covers mechanisms applied after or during generation.
These methods use compiler or runtime feedback for repair and combine LLMs with established
techniques such as search-based software testing [64, 100, 131, 166, 213]. These mechanisms aim to
improve executability, coverage, and fault detection.

Dataset construction and quality. Fine-tuning studies construct code–test corpora for adaptation

It has been used to generate tests for complex C++ projects [21] and exceptional behavior [219].

Test prefix and input generation

Test prefixes initialize objects, supply inputs, and invoke the focal method. Domain-specific input
constraints and precise initialization sequences make their construction difficult.
Semantic input construction. Methods for generating inputs construct concrete values, reusable
fixtures, object builders, mocks, or constraints for later generation. Bug reports, input partitions,
schemas, types, and mocking metadata guide these artifacts [105, 137, 172, 182, 239]. Equivalence
partitions and boundary values guide input design [150]. For fault-directed generation, Yin et
al. [209] adjust attention to defective statements. LISP generates executable drivers for library
APIs from input-space partitions [105]. Fixturize classifies whether a focal function or method
requires fixtures [172]. It routes functions needing no setup directly to test generation. For the
remaining functions, it refines invocation examples using runtime feedback, then uses these
examples to generate tests with setup, mocks, and inputs. Its asynchronous network example
shows why this preparation matters. An incomplete mock causes a TypeError because it omits
the methods needed to enter and exit the asynchronous context. For tests that require external
objects or mocked dependencies, ASTER identifies the relevant fields and types and incorporates
this information into a test skeleton [139]. CubeTesterAI provides focal-method, dependency, entity,
and DTO information in prompts with instructions for Mockito setup [61]. Valid inputs alone do
not ensure that a complete test compiles, exercises the intended behavior, or contains a correct
oracle [121, 207]. Once a complete test has been generated, model chaining can pass it to another
model for refinement [97].
Path-aware and constraint-guided generation. Path-sensitive approaches expose branch conditions,
semantic constraints, program graphs, symbolic results, or explicit exploration plans to focus
generation on hard-to-reach behaviors [10, 109, 113, 188, 191, 196, 216, 228]. SymPrompt enumerates
a minimized set of basis paths and constructs a separate prompt for each, using path conditions,
return behavior, and calling context. With CodeGen2, it produced approximately five times as many
passing tests that correctly called the focal method as its baseline completion prompt [152]. PALM
derives condition chains and project context from Rust MIR/HIR and control-flow analysis, repairing
path-specific tests with compiler feedback [37]. LLM4TDG uses constraint-dependency graphs and
backtracking to handle input requirements that must be satisfied together [113]. Structural analysis
gives generation explicit goals.

RQ1 Key Insight
Context-enriched generation: Many project-level generators supplement the focal
method with information needed to construct a test. Type and build information supports
executable setup, project tests and documentation guide API use and expected behavior,
and path or execution feedback directs further input generation. The design problem is
to select the information needed for each construction task and make it available to the
generator. Context construction is thus central to generation, alongside model adaptation.

RQ2 Key Insight
Engineering feedback in quality assurance: Many reviewed systems couple LLM generation with compilers, test runners, program-analysis or search tools, and mutation or
coverage feedback. These loops can improve executability, but they do not by themselves
establish semantic correctness, fault-detection effectiveness, or industrial reliability.

Challenges and Opportunities

The remaining challenges concern artifact trustworthiness, CUT and project complexity, and
evaluation validity. Project complexity can make it harder to construct a valid test, while incomplete
evaluation can hide whether similar improvements can be achieved in other tasks or repositories.
Fig. 7 relates them to parallel research directions in specifications and evaluation, project context
and tools, hybrid generation, and agentic workflows.
6.1

Challenges in automated test generation

6.1.1 Trustworthiness and correctness of test artifacts. Trustworthiness involves executable tests,
accurate oracles, fault detection, and maintainability. A generated suite can satisfy one of these
requirements while leaving others unresolved.
Low usability and high error rates. In AgoneTest’s initial configurations, build success ranged
from 7.1% to 36.0% across three models and zero- or few-shot prompts. Supplying the focal class’s
path raised these rates by 6.2 to 28.6 percentage points [121]. On Defects4J, the highest test pass
rate among Shang et al.’s fine-tuned models was 36.02%, with frequent build and syntax errors [155].
Yi et al. also reported syntax errors and non-existent method calls, with success depending on
prompts and project complexity [207]. Repair loops (Section 5.1) address these failures at the cost
of further model calls, compilation, and execution [64, 131].

The oracle problem and false positives. Syntax checks and text matching cannot establish oracle
correctness [76]. Work on assertion datasets, postconditions, and benchmarks with multiple program
variants makes expected behavior an explicit evaluation target [22, 93, 119, 125, 142, 157, 167].
Assertion errors accounted for 85.5% of failed executions in Yuan et al.’s analysis [213]. Numerical
tasks pose particular difficulties. Chang et al. report problems with arithmetic and loops [25], while
Koziolek et al. obtained no correct assertions for CRC_GEN despite full statement coverage with
both prompts [96]. However, failing assertions are not necessarily invalid. Mathews et al. show that
filtering tests that fail on the current implementation can discard tests exposing its defects [123].
Tests generated mainly from implementation code may reproduce a defect rather than expose it.
Huang et al. compared generation from correct and incorrect code, measuring test accuracy against
the datasets’ correct implementations. They found that incorrect input code could lead tests to
accept buggy behavior [80]. Documentation provides another source of intent [77], but ambiguous
requirements and disagreements with the implementation still require resolution.
Weak fault detection capability. Fault detection requires distinguishing faulty behavior, not simply
executing code. Reliability studies examine buggy input code, the validity of generated tests, and
the ability to expose real faults [29, 80, 164, 234]. On Defects4J, the best-performing model in Shang
et al.’s comparison, DeepSeek-Coder-6b, detected 8 of 163 bugs with 0.74% precision [155]. Here,
a bug-revealing test had to fail on the buggy version and pass on the fixed version. Using the
reported precision, this corresponds to roughly 135 failing candidates per bug-revealing test. The
low precision makes failure diagnosis part of the practical cost of generation.
Test smells and maintainability. Test smells flag potential maintenance problems [5, 136]. Magic
number test denotes unexplained constants in assertions, while assertion roulette involves multiple
unexplained assertions in one test method. In an HPC study, magic number test occurred in 100%
of generated tests and the human baseline [87], and approached 100% in several Java configurations [134, 135]. Another Java study found class-level assertion roulette rates of 54.77% with
TsDetect and 75.83% with JNose under zero-shot prompting [136]. Thus, test granularity, detectors,
and human baselines matter when interpreting smell counts.
6.1.2 Complexity of code under test (CUT). Project dependencies, complex control flow, and domainspecific behavior affect generation context and test execution environments. The selection methods
in Section 4.2 must work within finite context windows, while truncation can remove necessary
information [166]. CAT-LM’s 8,192-token window accommodated about 82% of its Java and Python
code–test file pairs [147]. Even with complete project code in the prompt, MultiFileTest reports
execution failures caused by a missing NumPy import [184]. The challenge is to select and correctly
use sufficient, trustworthy context within budget, not simply increase context length.
State transitions, numerical calculations, and parallel execution create different difficulties for
test generation. Koziolek et al.’s SEQUENCE_8 PLC block, containing 16 timers, reached 58.6%
statement coverage, but the environment did not simulate expiring timers [96]. This limits what the
result says about generation alone. Mokav reported failures on cases requiring precise mathematical
calculations [43]. In HPC testing, Karanjai et al. found missing or incorrect OpenMP pragmas,
erroneous method calls, and passing tests that did not explicitly check parallelism [87]. Inputs,
oracles, and execution environments therefore need to support the domain together.
Generation in a new project can also depend on the availability of local examples. JSONATG uses
historically failure-revealing demonstrations [180], while Shin et al. adapt models with developer
tests [156]. Projects with little testing history may lack these examples. TestGen-LLM’s authors
suggested that Facebook’s roughly tenfold larger pool of human-written Kotlin tests might explain
its slightly higher success rate than Instagram [6]. Testing adaptation on projects excluded from

6.1.3 Evaluation validity and ecosystem gaps. Model, prompt, and version choices can change the
apparent benefit of a generation technique [94, 134, 201]. Evaluation must therefore identify the
task, baseline, and deployment conditions under which an improvement is useful.
Data contamination and benchmark validity. Benchmarks now cover class-level, repository-level,
and reasoning-intensive generation tasks [25, 81, 83, 224]. MultiFileTest includes dependencies
across project files, TestGenEval uses repository test suites, and CLOVER evaluates context lengths
from 4k to 128k tokens [83, 184, 192]. SWT-Bench and TestEval further cover bug-reproduction
workflows and path-sensitive generation [127, 182]. Adversarial test generation and methods
targeting surviving mutants add further evaluation settings [26, 90]. Interpreting their results
requires knowing which mutants or other feedback were exposed during generation and which
cases were reserved for evaluation. These benchmarks broaden the tasks used for evaluation, but
task complexity alone does not determine whether a model has encountered the material.
Undisclosed training data make benchmark exposure difficult to establish. Public datasets such as
Defects4J may overlap with training corpora, allowing memorized artifacts to influence results [155,
179]. Azanza et al. selected functions and classes from projects without publicly accessible test
suites to limit reproduction of existing tests [15]. Reproducible comparisons need dataset and model
versions, separate development and evaluation examples, and reassessment after model updates.
Metric misalignment. Different subjects and success criteria complicate comparisons among
LLMs, search-based generators, symbolic execution, and prompts [1, 65, 106, 153, 166, 213]. Textmatching scores compare generated tests with reference tests. For complete test generation on
Methods2Test 𝑓 𝑖𝑙𝑡𝑒𝑟 , Shang et al. reported exact-match rates no higher than 0.55% [155]. Yet a
method can admit several valid tests, so divergence from a reference need not imply failure.
Conversely, textual similarity cannot determine oracle correctness or fault detection. Coverage and
mutation scores also depend on the testing objective. Zhao et al. found them useful for regressionstyle comparisons but unreliable when generation used buggy code to expose its defects [233].
Evaluation frameworks combine execution, cost, and other quality measures [8, 15, 38, 110, 130, 159].
Compilation and pass rates address executability [157, 167, 182]. Assessing test value additionally
requires measures suited to the objective, including oracle correctness, mutation or held-out fault
detection, maintainability, and cost, with failed generations included.
High cost and practical constraints. Workflow costs include adaptation, retrieval, repeated generation, build and test execution, and human review. Prompt efficiency, latency, carbon emissions, and
energy measurements capture different parts [98, 99, 133]. ChatTester averaged about 99 seconds
per test for generation and refinement, with about 15 seconds for initial generation and 30 per
refinement iteration [213]. Its authors attributed much of this time to API latency and compilation
or execution. Privacy and intellectual-property requirements can constrain deployment for proprietary code. Local open-source models offer an option [180], with infrastructure and maintenance
costs that must be included when comparing workflows.
6.2

Future opportunities

Models propose tests and interpret project information, compilers and runners expose execution
failures, and specifications and reviewers help determine intended behavior. TestForge’s iteration
study, CodaMosa’s search triggers, and work on documentation and user feedback illustrate different
divisions of responsibility [44, 77, 82, 100]. Comparisons under matched tasks and resource budgets
can identify which components contribute enough useful tests to justify their cost.

6.2.1 Agentic testing workflows. Agentic testing workflows allow a model to invoke development
tools and revise tests over multiple steps. SocraTest presented a vision of conversational testing
agents and an example of developer–LLM dialogue [46]. Agentic generators distribute planning,
generation, execution, and review across specialized or tool-using agents, including repository and
HPC settings [58, 88, 180, 190, 193, 225]. Design choices include combining agents’ tests, requesting
further generation or analysis, and validating candidates before developer review [13, 63, 148].
Order matters because generating faulty code first can lead subsequent tests to accept it [95].
Recording the inputs and outputs exchanged by agents and tools could locate such errors and trace
their propagation. Explicit tool interfaces would help reproduce these interactions.
TestForge refines an initial zero-shot suite with execution and coverage feedback. On TestGenEval,
coverage gains diminished after roughly ten iterations [82], motivating experiments on stopping
rules based on recent gains. CANDOR combines coverage-guided planning with specification-based
oracle review. On its Java datasets, removing the planner reduced coverage, while removing panel
discussion reduced oracle correctness [193].
Feedback can revise tests during a run or train models for later generation. Reinforcement learning
uses static quality scores or coverage rewards [160, 176, 218], while other workflows use repair
templates or agreement among candidates to revise or select tests during generation [64, 92, 163].
Retaining failures, successful repairs, or project conventions across runs could support later tasks.
Comparisons with and without this memory could track repeated mistakes and check for misleading
information after code changes to distinguish lasting adaptation from extra attempts at one test.
6.2.2 Hybrid integration with established testing techniques. Hybrid designs must decide which parts
of exploration and checking to delegate to established tools, and when model-generated candidates
are useful within that process. Search-based hybrids use models for stall recovery, population
initialization, type inference, and mutation [24, 53, 100, 189, 202]. The remaining question is
whether another model call adds more coverage or reveals more faults than continued search under
the same budget. Comparisons can vary trigger policies and ablate model roles, accounting for both
inference and execution costs. For symbolic hybrids (Section 5.2), comparisons can contrast models
that translate constraints into solver code with those that propose inputs directly [86, 181, 188].
Relevant outcomes are whether inputs reach the intended path, how failures guide subsequent
attempts, and the cost of each division of work.
6.2.3 Specification-driven testing. Documentation, requirements, user stories, and formalized specifications supply intent for oracle construction [52, 85, 111, 126]. Doc2OracLL found method
descriptions and @return tags to be the most useful Javadoc components [77]. Req2Test generates
unit tests from user stories and acceptance criteria through structured test planning [49]. As a
comparison, property-based systems generate properties and input strategies, considered separately from concrete-example suites here [108]. Each generated assertion could be linked to the
requirement it checks, with the relevant specification text retained alongside it. For example, an
assertion expecting an exception for empty input could be linked to the requirement that specifies
this behavior. This would make the basis for the expected result available during review and help diagnose disagreements between tests, code, and documentation. Incomplete, ambiguous, or outdated
specifications still require checking the interpretation and executable test. When requirements
change, these links could identify tests to revisit.
6.2.4 Expansion across the testing ecosystem. LLM applications span several testing levels and
domains [179]. Jiang et al.’s Python PathEval experiments and TrickCatcher’s EvalPlus experiments
focus on individual functions [86, 114]. Vertical integration across testing levels could translate
failures from existing integration or system testing into focused unit tests. This requires identifying

Studies of C, C++, Rust, games, and web components expose different build and context requirements [21, 32, 34, 112, 138]. HPC and production projects add execution and integration

A practical direction is to separate reusable generation procedures from project-specific language,
framework, and domain information. Tools could obtain build commands, fixture conventions, and
accepted test examples from the target project, reducing workflow redesign for each codebase.
Cross-project comparisons could then measure the setup and review effort that remains.
Human participation supplies testing intent and resolves uncertain expectations. In interactive
code generation, TiCoder requests feedback on tests to guide code selection, with a user study
examining code judgments and cognitive load [44]. UTGen’s developer experiment examines how
clearer test data, names, and comments support bug fixing [41]. These roles suggest requesting
feedback where context or expected behavior is ambiguous and retaining answers with the tests.
Comparing targeted questions with approval of every test could clarify the trade-off between
developer interruptions and unresolved oracle errors.
RQ3 Key Insight
Trustworthiness and practical value: Progress requires tests that run, check intended
behavior, expose faults, and remain useful to developers. Project context, independent
sources of intent, and evaluation of failures and workflow costs all contribute to these goals.
Agentic and hybrid workflows offer ways to combine these components, while human
review remains important where testing intent or oracle correctness is uncertain.

Threats to Validity

Threats to study selection. Search terms, incomplete abstracts, and gaps in database coverage
may cause relevant studies to be missed. Screening judgments and multiple reports of the same work
can also affect selection. To reduce these risks, we combined four core databases, two supplementary
sources, venue audits, and bidirectional snowballing. Two authors screened independently and
reconciled decisions, with reports linked before counting publications. Shared biases may remain,
and the requirement for accessible English full texts excludes non-English and unavailable reports.
Our scope also requires unit-test generation as a primary or co-primary objective and a newly
constructed unit-level artifact. Standalone repair, refactoring, migration, and improvement of
existing suites provide context only.
Threats to data extraction and synthesis. Subjective interpretation may cause extraction
errors or inconsistent taxonomy assignments, particularly because extraction was not independently
duplicated across the full provisional corpus. The 60-publication audit checked extraction, quality,
taxonomy, and execution classifications, while both authors independently classified 20 of the
audited publications without seeing the existing classifications. These checks confirmed the records,
but boundaries between context engineering, generation feedback, and downstream enhancement
remain interpretive. Errors outside the audited sample may remain undetected.
Threats to external validity. Concentration in Java, Python, and a few benchmarks limits
conclusions about other languages, projects, and industrial settings. The 47 publications represented
by preprints at the cutoff (26.4% of 178) may also change before formal publication. No principal
finding reversed in analyses of the 131 formal publications and 83 with explicit execution results.

Conclusion

This review synthesizes 178 publications on LLM-based unit-test generation in a lifecycle framework
connecting test construction with quality assurance. First, retrieval, static analysis, slicing, and
feedback supply the project dependencies and conventions needed to construct usable tests. Second,
generation is coupled to compilers, test runners, program analysis, and search. Compilation and
execution failures guide repair, coverage and mutation feedback guide further generation, and
filtering selects tests for the suite. However, repeated repair adds execution costs, and filtering
may discard useful tests. Third, agentic and hybrid workflows are expanding alongside persistent
problems with assertions, maintainability, benchmark validity, and the gap between coverage and
fault detection. Industrial use also requires managing dependencies, build environments, and costs.
Oracle correctness remains a central challenge because assertions can agree with faulty implementations. Alongside compilation and execution checks, expected outputs should be reviewed
using specifications or developer feedback. Tests against known faults reveal whether generated
suites detect incorrect behavior. Comparing original and repaired tests on the same faults can show
whether gains justify the additional execution and review effort.
LLMs now support unit-test generation, but their practical role depends on reproducible evaluation, independent validation of generated behavior, and appropriate human or tool supervision.
