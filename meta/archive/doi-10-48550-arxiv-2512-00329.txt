Abstract
Temporal reasoning over evolving semistructured tables poses a challenge to current
QA systems. We propose an approach that recasts the task as automated knowledge base
construction: (1) prompting an LLM to synthesize a 3NF-compliant relational schema from
Wikipedia infobox timelines, (2) populating
the schema to obtain a queryable database,
and (3) generating and executing SQL queries
against it, with QA accuracy serving as an extrinsic evaluation of the constructed knowledge
base. In a controlled grid of three schema
generators crossed with six query models, the
schema source accounts for 79.5% of the exact match (EM) variance against 1.6% for the
query model: replacing the schema, and the
prompt scaffolding derived from it, shifts EM
by 14.7 to 20.0 points, whereas replacing the
query model under a fixed schema shifts it
by 4.4 to 12.1. From this evidence, we distill three candidate schema-design principles:
balanced normalization, semantic naming, and
consistent temporal anchoring, framed as correlational hypotheses. Our best configuration
(Gemini 2.5 Flash schemas + Gemini-2.0-Flash
queries) reaches 80.39 EM, 11.5 points above
the strongest reported baseline (68.89 EM); an
open-weights configuration reaches 79.52.

Introduction

Large Language Models (LLMs) excel at understanding tabular data (Liu et al., 2024; Fang et al.,
2024), but struggle with temporal reasoning over
evolving semi-structured data. The T RANSIENTTABLES dataset (Shankarampeta et al., 2025) highlights this limitation by asking questions about
Wikipedia infoboxes sampled over time. Current
approaches treat these temporal infobox timelines
as text, forcing LLMs to perform implicit temporal reasoning across multiple table snapshots.

The T RANSIENT TABLES task: Given a series of
Wikipedia infobox snapshots for an entity (e.g., a
cricket team) sampled over time, answer natural
language questions that require temporal reasoning.
For example, "Who was India’s cricket captain before Rohit Sharma?" requires identifying temporal
ordering across snapshots, while "How many Tests
did India play between 2020 and 2023?" requires
aggregating time-bounded statistics.
We reframe temporal table reasoning as a textto-SQL problem, an approach we call E VI N ORM1

(Evidence-guided schema Normalization). Unlike standard text-to-SQL that assumes pre-existing
static schemas, we address the novel challenge
of synthesizing schemas from evolving semistructured data. Rather than asking LLMs to reason
over infobox timelines serialized as JSON strings,
we dynamically generate normalized database
schemas and leverage the LLMs’ ability to generate SQL. This offers three advantages: (1) explicit
temporal structure via timestamps and foreign keys,
(2) reduced ambiguity through schema constraints
and data normalization, and (3) access to SQL’s
temporal operators that directly map to the reasoning required (date arithmetic, window functions,
and temporal joins) (Liu et al., 2025). Unlike direct
text-based reasoning, which often fails on complex semi-structured data (Kulkarni et al., 2025;
Vo et al., 2022; Deng et al., 2025; Wu and Hooi,
2025), every answer is produced by an executed,
fully traceable query, enabling systematic debugging through prompt or schema refinement.
On T RANSIENT TABLES,
schema-guided
SQL generation improves substantially over the
strongest reported baseline (§5). More importantly,
our controlled comparison isolates where the
improvement comes from: decomposing the
variance of a 3 × 6 generator × query-model
grid attributes 79.5% of the EM variance to the
schema source and 1.6% to the query model. The
unit varied is a schema together with the prompt
scaffolding derived from it, not relational structure
in isolation.

Related Work

Our work sits at the intersection of tabular reasoning, temporal question answering, text-to-SQL
generation, and symbolic reasoning with LLMs. It
also connects to automated knowledge base construction: systems such as DBpedia (Auer et al.,
2007), YAGO2 (Hoffart et al., 2013), and Wikidata
(Vrandečić and Krötzsch, 2014) harvest structured,
temporally scoped knowledge from Wikipedia infoboxes into fixed ontologies, whereas we synthesize a task-specific relational schema with an LLM
and treat downstream QA as an extrinsic evaluation
of the constructed knowledge base. A natural alternative is to skip synthesis and query the curated
base directly, which would be cheaper to deploy
where applicable. We do not report that comparison. It is not like-for-like here, since T RANSIENTTABLES answers are defined relative to specific
infobox revisions whereas Wikidata statements and
their start time/end time qualifiers are curated
on a separate editorial track; and it trades schema
synthesis for ontology mapping rather than removing it, since infobox fields must still be aligned to
properties that may not exist for long-tail entities.
Quantifying how much of T RANSIENT TABLES can
be answered directly from Wikidata is left to future work. We frame temporal table reasoning as
schema synthesis followed by schema-guided SQL
generation, and position our contribution relative
to each line of work below.
Tabular Reasoning. Research on semistructured tables spans inference and question
answering (Gupta et al., 2020), fact verification
(Chen et al., 2020), conversational summarization
and exploration (Zhang et al., 2020), and table
retrieval and augmentation (Zhang and Balog,

2020). Neural encoders such as TAPAS (Herzig
et al., 2020), TaBERT (Yin et al., 2020), and
TABBIE (Iida et al., 2021) learn joint table–text
representations, while Table2vec (Zhang et al.,
2019) and TabGCN (Pramanick and Bhattacharya,
2021) explore alternative table encodings. Closer
to our work, symbolic approaches such as BINDER
(Cheng et al., 2023), DATER (Ye et al., 2023),
and Chain-of-Table (Wang et al., 2024) interleave
language models with executable programs over
tables, but all operate on a given, fixed table
or schema. Our setting differs fundamentally:
no schema exists, and the structure itself must
be synthesized from evolving input before any
reasoning can occur.
Temporal Question Answering. Datasets such
as TIME-SENSITIVEQA (Chen et al., 2021),
TORQUE (Ning et al., 2020), TEMPQA-WD (Neelam et al., 2022), and CRONQUESTIONS (Saxena et al., 2021) capture temporal dependencies
in text and curated knowledge graphs; TempTabQA (Gupta et al., 2023) and TRAM (Wang and
Zhao, 2024) extend temporal evaluation to tables,
though without explicit schema normalization. All
of these operate over a single table snapshot or
a static knowledge graph. T RANSIENT TABLES
(Shankarampeta et al., 2025) is, to our knowledge,
the only public benchmark whose instances are sequences of table snapshots; this state-change signal
is precisely what our schema-synthesis approach
exploits (§4).
Text-to-SQL and Schema Design. Text-to-SQL
has progressed from schema-linking architectures
(Guo et al., 2019; Wang et al., 2020) and constrained decoding (Scholak et al., 2021) to LLMera benchmarks targeting robustness and scale (Yu
et al., 2019; Gan et al., 2021; Lei et al., 2025;
Liu et al., 2025); temporal SQL over versioned
databases has a long history in the database community (Vo et al., 2022; Snodgrass, 1999). This
literature almost universally assumes a pre-existing,
human-curated schema. Most directly related,
Kohita (2025) systematically studies the effect
of normalization on SQL generation over given,
static schemas, finding that normalized (2NF/3NF)
schemas introduce challenges such as base-table selection and join-prediction errors. Our work differs
on three axes. First, the setting: no schema is given,
so an LLM must synthesize it from raw, evolving
JSON timelines, and this synthesis step is what

we systematically study. Second, the direction of
the finding: in the temporal regime we observe the
converse and more nuanced trade-off, where balanced normalization helps, because it is precisely
what makes snapshot joins expressible, while overnormalization hurts (§6.1). Third, our temporalanchoring principle (a uniform snapshot_id key
enabling equality joins across time-varying tables)
has no analog in static text-to-SQL.
Symbolic Reasoning with LLMs. NL2FOL
(Lalwani et al., 2025), LOGIC-LM (Pan et al.,
2023), and LINC (Olausson et al., 2023) demonstrate that mapping language into formal representations improves inference robustness, and LLMsymbolic integration has been applied to temporal
tabular reasoning (Kulkarni et al., 2025; Kulkarni
and Srikumar, 2025; Deng et al., 2025; Wu and
Hooi, 2025). We instantiate this program with relational algebra as the formal system and show that
the quality of the constructed symbolic representation accounts for more of the variance in downstream accuracy than the capacity of the model
querying it.

3

Methodology

Task Definition. An instance consists of an entity
e with a timeline Se = {(t1 , J1 ), . . . , (tk , Jk )} of
k (typically 8–12) timestamped snapshots, where ti
is the timestamp of a Wikipedia revision and Ji is
that revision’s infobox serialized as a JSON object
mapping attribute names to values, and a naturallanguage question q whose answer requires reasoning across multiple snapshots: temporal ordering,
concurrency, aggregation over bounded intervals,
or duration. Successive Ji are neither identical nor
schema-aligned: attributes appear, disappear, are
renamed, and change value between snapshots, and
it is precisely this state-change signal that the question set targets. Given (Se , q), the system must
produce the answer a.
E VI N ORM transforms this temporal table reasoning task into a text-to-SQL problem through
three stages: (1) dynamic schema generation from
temporal infoboxes, (2) database population with
cleaned data, and (3) schema-guided SQL generation with few-shot prompting.
3.1

Normalized Schema Generation

Given the snapshots Se , we generate a normalized
relational schema using LLMs: the model receives
2-3 example JSON timelines from the same domain

and is prompted for a Third Normal Form (3NF)
schema. It produces four table types:
• Entity tables: Core entities with unique identifiers (e.g., Countries, Leaders, Players)
• Attribute tables: Domain-specific lookup tables
(e.g., LeaderRoles, MatchFormats)
• Snapshot tables:
Temporal data with
snapshot_id as timestamps, containing
time-varying attributes
• Bridge tables: Many-to-many relationships linking entities, attributes, and time periods (e.g.,
SnapshotLeaders)
Normalization rationale. 3NF reduces redundancy across temporal snapshots by factoring
out repeated information. Schemas are explicitly prompted for 3NF and manually validated for
atomicity of values, complete dependency on primary keys, and absence of transitive dependencies.
We do not formally prove 3NF compliance; Appendix A.5 gives the validation procedure and examples.
3.2

Schema Tables (database) population

Automated Python scripts populate SQLite
databases from LLM-generated schemas, handling
date format variations, text normalization, and referential integrity validation (more details in Appendix A.6).
3.3

Schema-Guided SQL Generation

Few-shot Examples Construction. We build
one exemplar per question type. T RANSIENT TA BLES instantiates ten to fifteen recurring question
templates in each domain, and we take a single
question from each, so the exemplar set covers the
domain’s question taxonomy uniformly instead of
over-representing any one pattern. Given a question Q with expected answer A, we prompt the
model with the schema, Q, A, and database access;
it proposes an SQL query, executes it, compares
the result to A, and refines until exact match. The
resulting “gold queries” span before/after ordering, concurrent roles, temporal aggregation, tenure
duration (JULIANDAY() arithmetic), and temporal
extrema.
Few-shot Provenance. The question-answer
pairs used to construct gold queries are drawn exclusively from the T RANSIENT TABLES development split, one per question template; no test-set
question appears as a few-shot exemplar in any domain. Execution-based refinement accesses only

the populated database, never test-set answer keys.
Because T RANSIENT TABLES questions instantiate
recurring temporal templates by design, our exemplars reflect those templates, as do the IRE+CoT
baseline’s CoT exemplars; the comparison is fewshot SQL against few-shot CoT, not against zeroshot.
Domain-specific Prompting. Domain-specific
prompts include: (1) complete schema with constraints, (2) natural language descriptions of key
relationships, (3) 8-10 SQL templates, (4) 1015 few-shot examples, and (5) critical rules (e.g.,
“Never hardcode entity IDs; always use subqueries”,
“Use DISTINCT for queries spanning multiple snapshots”). Unlike generic text-to-SQL prompting
(Lei et al., 2025), this encodes temporal semantics (snapshot_id ordering, JULIANDAY() arithmetic) and domain constraints directly, narrowing
the search space from all well-formed SQL to temporally valid queries. Appendix A.1 walks a single question through all three stages, from infobox
snapshots to executed SQL, and Appendix F.1 lists
the complete synthesized Countries schema.
Query Generation and Evaluation. At test time,
given question Q from T RANSIENT TABLES, we
concatenate the domain prompt with Q and query
the SQL generation LLM. The model generates an
SQL query, which we execute on the corresponding
SQLite database. We compare the retrieved result
to the expected answer using Exact Match (EM),
token-level F1, Rouge-1, and Rouge-L scores.
Domain-Generality of the Pipeline. The
pipeline contains no benchmark-specific machinery; Appendix A.3 sets out the cost of adapting it
to a new semi-structured source.

Experiments

Benchmark: We evaluate on T RANSIENT TA BLES (Shankarampeta et al., 2025): 3,971 questions derived from over 14,000 table revisions spanning 1,238 entities, grouped into 10 structurally
distinct entity domains (countries, economies, government agencies, and seven sports domains), with
each entity represented by 8–12 infobox snapshots.
The number 10 refers to domains, not entities: each
domain contains on the order of a hundred distinct entities, and every reported score is a domainlevel average over that domain’s evaluation questions. We use this single benchmark deliberately:
to our knowledge, it is the only publicly avail-

able benchmark of multi-snapshot temporal semistructured tables. Existing temporal QA datasets
such as TempTabQA (Gupta et al., 2023), TIMESENSITIVEQA (Chen et al., 2021), CRONQUESTIONS (Saxena et al., 2021), and TEMPQA-WD
(Neelam et al., 2022) contain single-snapshot tables or static knowledge graphs; repurposing them
would either discard the state-change signal our
method targets or require synthetic snapshot generation.
Model selection: We select models to vary the
capability tier and openness rather than to survey
the frontier. The open-weights side spans an order
of magnitude within one family (Llama-3.1-8BInstruct, Llama-3.3-70B-Instruct) plus a second
family at the small end (Qwen-2.5-7B-Instruct),
separating scale effects from family effects; the proprietary side spans two tiers of one family (Gemini2.0-Flash, Gemini-2.5-Pro) and a compact model
from another (GPT-4o-mini). We use instructiontuned checkpoints throughout because every stage
is prompted and never fine-tuned, and base checkpoints do not reliably respect the output-format
constraints the prompts impose. Schema generators are drawn from the same pool, so for two of
the three, the same model also appears as a query
model.
Baseline: We compare against InformationRetrieval-Extraction with Chain-of-Thought
(IRE+CoT), the strongest of the four prompting
strategies reported by Shankarampeta et al.
(2025) and the published state of the art on this
benchmark. It is also the closest structural match
to our pipeline: it decomposes the task into stages
(retrieve snapshots, extract attributes, reason) and
supplies few-shot exemplars, so the comparison is
few-shot SQL against few-shot CoT rather than
against a zero-shot control. We reuse the published
per-model numbers and evaluate our pipeline with
the same six query models.
Normalized Schema Generation LLMs:
Schemas are generated by Gemini 2.5 Flash
(Comanici et al., 2025), Llama 3.3-70B-Instruct
(Grattafiori et al., 2024), and Llama 3.1-8BInstruct. Each generator sees 2–3 example
timelines per domain and emits one 3NF schema
per domain in a single prompted call, giving 10
schemas per generator, each reused unchanged
for every entity and question in its domain. We
neither re-sample schemas per entity nor measure
run-to-run variability of the synthesis step, so the

effect sizes we report are between-generator rather
than between-run (see Limitations). We additionally synthesize schemas with GPT-5.4-mini as an
out-of-family robustness check. GPT-5.4-mini
is used for schema synthesis only and never
for query generation; the resulting schemas are
queried by three of the six models listed below (§5,
Appendix B) and are reported separately from the
main grid.
SQL Query Generation LLMs: We evaluate six
query models: Gemini-2.0-Flash, Qwen-2.5-7BInstruct (Bai et al., 2023), Llama-3.1-8B-Instruct,
Llama-3.3-70B-Instruct, GPT-4o-mini (Hurst et al.,
2024), and Gemini-2.5-Pro.
Decoding: All stages use temperature = 0.1,
top-p = 0.9, and a 2048-token generation limit.
Database population and few-shot exemplar construction follow §3.

Analysis

6.1

Schema Design Principles

What makes a synthesized schema effective? We
quantify structural properties of the generated
schemas and relate them to downstream QA accuracy. For each domain, we compute four fragmentation metrics over the populated database: completeness (C, the fraction of base identifiers that participate in each fragment), losslessness (R, whether
identifiers are reconstructible from unions of fragments), referential consistency (RC, whether all
foreign keys resolve), and disjointness (D, the absence of duplicated fact units). Together with join
depth and table counts, these metrics reveal concrete patterns underlying the performance differences:
Fragmentation and Join Complexity: Gemini
2.5 Flash generates the most compact schemas (5.5
tables/domain against 7.7 for Llama-3.1-8B and
6.2 for Llama-3.3-70B; Table 3, right) and the shallowest joins (1.089 average depth; left). Excessive
fragmentation, notably in data-rich domains such
as Economy (18 tables with Llama-3.1-8B against
2 with Flash), and high join depth (Government
Agencies: 2.03-3.65) both track increased SQL
generation errors, consistent with our balancednormalization principle.
Fragmentation Quality: Tables 16-18 reveal
that all schema generators maintain high referential consistency (RC = 1.0) and losslessness
(R ≥ 0.96 for most domains), but differ in completeness. Flash schemas achieve C ≥ 0.92 in
6 of 10 domains, with the remaining deviations

attributable to domain semantics (optional annotations, sparsely populated roles) rather than schema
defects, while maintaining simpler structures that
facilitate SQL generation.
Case Study: Balanced vs. Over-Normalized
Schemas. Gemini-2.5-Pro schemas enter our
structural analysis but were not swept across the
query grid, so this is evidence about query complexity, not a measured accuracy gap. For “Who
was the coach when Balaji Pai was T20I captain?”
the Flash schema answers in 6 lines over 4 tables by joining role-specific tables on the shared
snapshot key, while Pro routes both roles through
generic People/Roles tables, forcing 15 lines
over 6 tables including a self-join (Appendix E.1).
Over-normalization is not wrong relationally, it is
costly generatively: every additional join is another
chance for the query model to err.
What these metrics do and do not certify. C,
R, RC, and D are intrinsic measures, computed on
the populated database independently of any question: they establish that the artifact is well formed
and that no base identifier is lost under fragmentation. They are silent on semantic fidelity, saying
nothing about whether each fact reaches the right
relation and column, whether values survive cleaning undistorted, or whether a row is traceable to the
revision that produced it. A schema could score
perfectly while mis-assigning a role the benchmark
never probes, and downstream accuracy, our only
other check, rewards representations suited to this
question distribution. Auditing fact-level mapping
accuracy and provenance against sampled snapshots is the intrinsic evaluation that this line of
work most needs (Limitations).

6.3

Cost and Efficiency

Schema synthesis is a one-time offline cost per
domain: a single LLM call over 2-3 example timelines, after which the schema is reused for every
question in that domain and adds no per-query latency. Few-shot exemplar construction is likewise
offline and bounded by a single pass over the development questions. At inference time, the pipeline

reduces to a single SQL generation call plus local
SQLite execution (milliseconds). Notably, our best
configuration relies on smaller, cheaper models
(Gemini 2.5 Flash for schemas, Gemini-2.0-Flash
for queries) than the strongest baseline (Gemini2.5-Pro with IRE+CoT), yet scores 11.5 EM points
higher, so the accuracy gains do not come at the
price of a heavier stack.
Average prompt and completion tokens per
SQL-generation call are nearly flat across schema
sources (3752 to 4230 total, a 13% range) while
the best EM attainable with each schema spans
15.6 points, so accuracy differences are not bought
with inference budget; Appendix C gives the breakdown.

7

Discussion

Scope of the claims. Our design principles are
hypotheses supported by controlled comparisons
on one benchmark, grounded where possible in
database theory: snapshot-anchored tables mirror
SQL:2011 system-versioned temporal tables (Snodgrass, 1999), and semantic naming accords with
schema-ambiguity findings in static text-to-SQL
(Kohita, 2025).
Reading behavior off closed models. Two of
our four schema generators are proprietary systems whose training is undisclosed, so explaining
why their schemas differ risks reverse-engineering
a black box. We keep our claims to what is observable: the schemas are inspectable artifacts, and
join depth, table count, naming style, and temporal
anchoring are properties of those artifacts rather
than inferences about model internals. The central finding does not rest on closed models in any

case. The schema effect is just as clear among the
open-weights generators (Llama-3.3-70B schemas
at 77.21 EM on average against Llama-3.1-8B at
62.31), and the best open-weights configuration
lands within 0.9 EM of the best overall, so both
pipeline and conclusion are reproducible without
proprietary access.
What would falsify the principles. Because generator identity, naming style, and table granularity
co-vary in our data, the principles are hypotheses
with a concrete test: perturb one fixed schema, one
factor at a time, preserving information content,
and read off the EM deltas. Limitations give the
design; we regard it as the most valuable single
addition to this work.
Fragility is real but asymmetric. A schema
error cascades through every downstream query,
a single point of failure that retrieval-based approaches do not share. Empirically such errors are
rare (6% of failures; §6.2), and current LLMs prove
strikingly reliable at producing referentially consistent structure (RC = 1.0 across all generators).
But rare-and-catastrophic is a different risk profile
from frequent-and-recoverable, which makes automated schema verification a high-value direction
for future work (Appendix A.4).
Implications for knowledge base construction.
The variance asymmetry suggests a division of labor for LLM-era knowledge base construction: invest model capability in constructing the representation, then exploit it with inexpensive query models. Well-normalized schemas transfer across all
six query models we test, so the recipe is not tied
to any proprietary system.

8

Conclusion

We presented E VI N ORM, a SQL-based approach to
temporal reasoning over evolving semi-structured
tables that synthesizes normalized schemas rather
than assuming them. Across three schema generators and six query models on T RANSIENT TA BLES , the choice of schema source accounts for
a far larger share of the variance in QA accuracy than the choice of query model: 79.5% of
the EM variance across the grid against 1.6%, or
14.7 to 20.0 points of swing from replacing the
schema against 4.4 to 12.1 points from replacing the query model, though the margin narrows
once the weakest generator is set aside (§5). The
unit being varied is a schema together with the

prompt scaffolding derived from it, and the evidence is associational, since generator identity,
naming style, and table granularity co-vary. From
this evidence, we distill three candidate design principles for temporal QA systems: balanced normalization outperforms excessive fragmentation; semantic naming reduces token-level confusion relative to generic abstractions; and consistent temporal anchoring enables pattern transfer across domains. We frame these as empirically supported
hypotheses, grounded in database theory, in which
snapshot-anchored tables mirror SQL:2011 systemversioned temporal tables, rather than as established universals: information-preserving schema
perturbations would be needed to determine which
property does the work. For automated knowledge
base construction more broadly, our results suggest
a division of labor: invest model capability in constructing the structured representation once, then
exploit it with inexpensive query models.

Limitations
Attribution of the schema effect: Our few-shot
exemplars, relationship descriptions, and SQL templates are derived from each schema, so replacing a
schema replaces the entire prompt scaffolding built
on it. The controlled comparison in Table 1 therefore measures the effect of a schema together with
its induced scaffolding, under a fixed construction
procedure, and cannot separate the contribution of
relational structure from that of the surrounding
prompt. Statements about the schema being the
dominant lever should be read with that unit of
comparison in mind. A zero-shot condition and a
shared-few-shot condition, crossed with the three
generators, would separate the two; we did not run
them.
Correlational design principles: Normalization
depth, naming style, temporal anchoring, and generator identity co-vary across the schemas we compare, so the three design principles are hypotheses consistent with our measurements rather than
isolated causes. Establishing causality requires
information-preserving perturbations of a single
schema, varying one property at a time: renaming
tables and columns to opaque identifiers while holding structure constant (semantic naming); merging
or splitting relations while preserving the same
functional dependencies (balanced normalization);
and replacing the uniform snapshot_id with pertable date columns carrying identical information

(temporal anchoring). Each perturbation preserves
the knowledge base’s information content and
changes only the property under test. Until such
an ablation exists, the principles should be treated
as design heuristics with empirical support on one
benchmark, not as established results.
Schema-generation variability: Each generator
produces one schema per domain in a single call,
decoded at temperature 0.1, and that schema is
reused for every entity and question in the domain.
We therefore report between-generator differences
and do not measure how much a generator’s schema
varies across independent runs of generation. Because we argue that the schema matters a great
deal, run-to-run variance is exactly the quantity
a follow-up should report: repeated synthesis per
domain, with the resulting spread in downstream
EM, would show whether the gaps in Table 1 are
stable properties of a generator or partly draw from
a wide distribution.
No intrinsic evaluation of semantic fidelity:
Our structural metrics (completeness, losslessness,
referential consistency, disjointness) certify that
the constructed knowledge base is well-formed,
but not that it faithfully preserves the source. We
do not measure fact-level mapping accuracy, value
fidelity under cleaning, or provenance from individual snapshots; downstream QA accuracy serves
as a proxy that rewards representations suited to
this benchmark’s question distribution (§6.1).
Single benchmark evaluation: Our empirical
validation is confined to the T RANSIENT TABLES
benchmark. To our knowledge, it is the only publicly available benchmark of multi-snapshot temporal semi-structured tables; repurposing singlesnapshot or static-KG temporal QA datasets would
eliminate the state-change signal our method exploits. Nevertheless, validation across additional
sources (e.g., corporate databases, temporal knowledge graphs, or other domain-specific temporal
QA tasks) would strengthen generalizability claims.
We also do not compare against querying an existing curated temporal knowledge base, such as Wikidata or YAGO2, directly; an alternative that would
be cheaper to deploy where it applies, measuring
how much of T RANSIENT TABLES is answerable
from those sources is left to future work (§2).
A comparatively clean data source: Wikipedia
infoboxes are curated, actively maintained, and

already reasonably regular, which makes them a
favorable setting for schema synthesis. Real deployments, particularly in industry, involve missing
fields, inconsistent or undocumented schemas, contradictory records, and structures that change more
often and less predictably than an infobox does.
Our population layer handles a catalog of concrete
inconsistencies (Appendix A.6), but that catalog
was assembled against this source. How far synthesis quality degrades as the source gets noisier is an
open question our experiments cannot answer, and
the 70% of residual errors we attribute to data understanding (§6.2) suggests the degradation could
be steep.
Single-domain restriction: Our current implementation limits queries to a single entity domain
(e.g., only cricket teams or only countries). Crossdomain queries like “Who was India’s cricket captain when GDP growth exceeded 7%?” would require joining schemas from different domains, introducing significant computational and modeling
complexity.
Schema generation dependency: Performance
is highly sensitive to schema quality. A single normalization error, such as failing to create a bridge
table for a many-to-many relationship, cascades
through all queries using that schema. This creates
a single point of failure that is absent in retrievalbased approaches.
No handling of uncertainty: Our approach generates deterministic SQL queries that return exact
answers. However, many temporal questions involve uncertainty (e.g., “approximately when did
X begin?”). SQL’s boolean logic cannot naturally
express probabilistic or fuzzy temporal boundaries,
forcing binary decisions where gradual transitions
would be more appropriate.
Wikipedia-specific data assumptions: Our data
cleaning pipeline is tuned for Wikipedia infobox inconsistencies (date format variations, nested arrays,
key naming variations). Applying this approach to
other semi-structured sources (corporate databases,
government records, scientific datasets) would require substantial re-engineering of the cleaning
logic.

Ethical considerations
This study uses only publicly available Wikipedia
infobox timelines from the TransientTables bench-

mark and involves no human subjects, private data,
or sensitive attributes; all entities correspond to
public figures or institutions. Our SQL-based
framework for temporal reasoning produces verifiable, traceable outputs that minimize subjective
or value-laden interpretations, while the use of normalized schemas constrains model generations and
mitigates bias. Although large language models
(e.g., Gemini and Llama variants) may inherit pretraining biases, our system’s reliance on deterministic SQL execution limits the propagation of such
biases. Potential downstream impacts include misinterpretation or overreliance on automated schema
designs when applied to high-stakes domains such
as healthcare or finance. To mitigate these risks,
we recommend human validation, transparent documentation of schema transformations, and maintenance of audit logs for all generated queries. All
experiments were conducted on open data in accordance with the ACL Ethics Policy, and any released
code or derived data will be distributed solely for
research purposes under terms that encourage transparency and responsible reuse.

A.1

A Worked Example, End to End

This section follows one question through all three
stages of E VI N ORM, using the cricket_team domain and the schema synthesized by Gemini 2.5
Flash. The question is “Who was the coach when
Balaji Pai was T20I captain?”, a concurrency question: it asks which value one attribute held at the
time another attribute held a given value, so it cannot be answered from any single snapshot in isolation.
Input: an infobox timeline. The pipeline receives Se , a sequence of timestamped infobox snapshots for one entity. Schematically, with values
elided and keys abridged:
2015-03-12: {"coach": ..., "captain (T20I)":
...,
"T20I rank": ..., "T20I record":
...}
2016-07-04: {"coach": ..., "captain (T20I)":
...,
"T20I rank": ..., "T20I record":
...}
2018-01-22: {"coach": ..., "captain (T20I)":
...,
"T20I rank": ..., "T20I record":
...}

The same keys recur across timestamps while their
values change, and keys are occasionally added or
dropped between revisions. This is the state-change
signal the schema must capture.
Stage 1: schema synthesis. A single prompted
call over 2–3 such timelines returns a 3NF schema
for the whole domain. The four tables relevant to
this question are reproduced below (the full schema
is listed in Appendix F.2):
Coaches (coach_id PK, coach_name)
Players (player_id PK, player_name)
CaptainRoles (captain_role_id PK, role_title)
TeamSnapshots (snapshot_id PK, team_id FK,
coach_id FK, t20i_rank, ...)
TeamCaptaincy (snapshot_id FK, player_id FK,
captain_role_id FK)

Three design decisions matter here.
Timevarying attributes live in TeamSnapshots, keyed by
snapshot_id; the many-to-many relation between
players and captaincy roles at a point in time is
factored into the bridge table TeamCaptaincy; and
both tables are anchored on the same snapshot_id
vocabulary, which is what makes “at the same time
as” expressible as an equality join rather than an
interval comparison.

Stage 2: population. Automated scripts parse
the CREATE statements, clean each snapshot’s
values (date normalization, entity-name normalization, type coercion, null handling), and insert rows, rejecting any row that violates a declared foreign key. Each infobox revision becomes one TeamSnapshots row plus zero or more
TeamCaptaincy rows.
Stage 3: SQL generation and execution. The
domain prompt supplies the full schema, naturallanguage descriptions of the relationships, 8–10
SQL templates, 10–15 execution-validated exemplars, and the critical rules listed in §3. The query
model then emits:
SELECT DISTINCT c.coach_name
FROM Coaches c
JOIN TeamSnapshots ts ON c.coach_id = ts.
coach_id
JOIN TeamCaptaincy tc ON ts.snapshot_id = tc.
snapshot_id
JOIN Players p ON tc.player_id = p.player_id
JOIN CaptainRoles cr
ON tc.captain_role_id = cr.
captain_role_id
WHERE cr.role_title = ’T20I Captain’
AND p.player_name = ’Balaji Pai’
AND ts.team_id = (SELECT team_id FROM
CricketTeams
WHERE team_name =
’Gibraltar national cricket
team’);

The temporal condition is carried entirely by
ts.snapshot_id = tc.snapshot_id: coach and
captain are required to be recorded in the same revision. The query is executed against the populated
SQLite database and its result is compared to the
reference answer under Exact Match, token-level
F1, Rouge-1, and Rouge-L. Appendix E.1 shows
what the same question costs under a more heavily
normalized schema, where both roles route through
generic People/Roles tables and the query needs
a self-join over personnel.
A.2

Temporal Coverage: An Allen-Interval
View

Allen’s interval algebra (Allen, 1983) defines 13
basic relations between time intervals and provides
a natural yardstick for the temporal scope of our
approach. Our few-shot SQL templates compile
into predicates over snapshot ranges that natively
express 11 of the 13 relations: before/after map to
strict inequalities on snapshot bounds (e.g., s1.end
< s2.start), meets/met-by to boundary equality (s1.end = s2.start), and overlaps, during,
starts, finishes and their inverses to conjunctions

of <, =, > over interval endpoints. The remaining relations equals on closed intervals and strict
containment are handled via window functions or
LEAD/LAG, which our templates employ for tenure
and succession questions. This mapping makes
the theoretical scope of the approach explicit: deterministic SQL over snapshot-anchored schemas
covers the full qualitative interval calculus, whereas
metric vagueness (“around 2020”, “early career”)
lies outside Boolean semantics (see Limitations).
A.3

Domain-Generality of the Pipeline

The pipeline contains no benchmark-specific machinery. Schema synthesis consumes only 2–3 example timelines and no Wikipedia-specific heuristics; few-shot exemplars are constructed automatically via execution-based validation rather than
manual curation, making them reproducible for
any new domain at the cost of a small development
set; and the population layer’s defensive strategies (null normalization, type-conversion fallbacks,
constraint-violation handling) are standard for any
semi-structured source. The main adaptation cost
for a new data source is the set of composite-field
parsers described in Appendix A.6.
A.4

Future Works

Cross-domain temporal reasoning: Extending
our approach to support queries spanning multiple
entity domains (e.g., "What was India’s GDP when
Virat Kohli became captain?") requires developing
schema integration techniques and multi-database
join strategies while maintaining temporal consistency across heterogeneous schemas.
Generalization beyond Wikipedia: Adapting
our schema generation and data cleaning pipeline to
corporate databases, government records, and scientific datasets would require domain-agnostic normalization strategies and automated schema quality
assessment tools.
Automated schema optimization: Developing
methods to automatically evaluate and refine
schema designs based on query performance patterns could reduce the dependency on initial
schema quality and enable adaptive normalization
strategies.
A.5

3NF Validation

We implement automated Python scripts to create and populate SQLite databases from the LLMgenerated schemas. The pipeline includes: (1) pars-

ing SQL CREATE statements to instantiate tables,
(2) cleaning JSON data to handle inconsistencies
in Wikipedia infoboxes (e.g., date format variations, text normalization, nested structure parsing),
(3) executing INSERT statements with proper type
conversion, and (4) validating referential integrity
constraints. Semi-structured JSON infoboxes exhibit high variability across domains, for example,
handling inconsistencies such as “Prime Minister”
vs. “PM”, malformed arrays, and missing values,
necessitating defensive parsing and cleaning strategies
Given a set of JSON-formatted Wikipedia infobox snapshots for an entity (typically 8-12 temporal samples), we generate a normalized relational
schema using LLMs. We provide the model with 23 example JSON timelines from the same domain
and explicitly request a Third Normal Form (3NF)
schema, in line with standard database normalization principles.
For example, rather than storing “Prime
Minister: Angela Merkel” in 20 consecutive snapshots, we normalize to three tables: Leaders(leader_id,
leader_name),
LeaderRoles(role_id,
role_title), and
SnapshotLeaders(snapshot_id, leader_id,
role_id). This structure explicitly represents temporal state changes through foreign key relationships, enabling SQL’s temporal operators (date
comparisons, temporal joins, and window functions) to express complex temporal reasoning patterns.
Ensuring 3NF Compliance. We employ a threestep validation process:
(1) Explicit prompting: Our schema generation prompt explicitly instructs: “Generate a 3NF
schema where: (a) all attributes are atomic (no
multi-valued fields), (b) all non-key attributes are
fully functionally dependent on the primary key,
and (c) no transitive dependencies exist between
non-key attributes.”
(2) Manual structural inspection: Each generator emits one schema per domain, so ten schemas
per generator, all of which we inspected; within
them we audited 50 randomly sampled tables per
generator in detail against the 3NF criteria:
• Atomicity: No composite values (e.g., “Name
(Role)” split into separate columns)
• Full dependency: All attributes depend on the
entire primary key, not a subset

• No transitive dependencies: No attributes A →
B → C chains where C depends on A through
B

A.6.1 Data Type Conversion Errors
Wikipedia infoboxes contain numeric values with
formatting inconsistencies (e.g., “1,234”, “1.0”,
“∼100”). Direct conversion to SQL integer/float
types fails. We implement a safe integer parser
that:
• Strips commas and whitespace
• Converts to float first (handles “1.0” → 1)

• Special characters:
“31/&ndash;”

“2/22”

“catches/stumpings”:

We implement domain-specific parsers that:
1. Normalize null values.
2. Use regex-based extractors for composite fields.
3. Handle dynamic field names with pattern matching.
Rationale. JSON’s semi-structured nature allows
field structures to vary across domains and even
within records. This unpredictability makes direct schema mapping prone to errors. Our robust
parsing strategies like defensive fallbacks, domainspecific extractors, and standardization layers handle this variability.
